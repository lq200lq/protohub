## 1. 存储抽象与目录布局

### 1.1 StorageAdapter 接口（决策 D-08）

```ts
// apps/server/src/storage/storage.adapter.ts
export interface StorageAdapter {
  /** 把本地文件放到指定 key（上传/落盘） */
  putFile(localPath: string, key: string): Promise<void>;
  /** 读取对象（本地实现返回 createReadStream；S3 实现返回 HTTP 流的 Promise） */
  getStream(key: string): Promise<NodeJS.ReadableStream>;
  /** 递归删除一个前缀（GC 用） */
  deletePrefix(keyPrefix: string): Promise<void>;
  exists(key: string): Promise<boolean>;
  /**
   * 列出某个前缀下的**直接子项**（GC 的三处扫描共用：trash 到期、tmp 残留、孤儿目录）。
   * 前缀不存在 = 空数组，不抛错。
   */
  listPrefix(keyPrefix: string): Promise<StorageEntry[]>;
  /** 把某个前缀原子地移出服务范围（本地实现 = rename 到 trash；S3 实现 = 复制后删） */
  moveToTrash(keyPrefix: string): Promise<string>;
  /** 仅本地实现有：给出绝对路径，供 nginx alias 与开发期 Node 直出使用 */
  localPathOf(key: string): string | null;
}

/** `listPrefix()` 的一行：key / 是否目录 / mtime / 字节数（目录是递归累计） */
export interface StorageEntry {
  readonly key: string;
  readonly isDirectory: boolean;
  readonly mtimeMs: number;
  readonly sizeBytes: number;
}
```

> **修订说明（M5-T6，迭代实施计划 §9.2 DEV-41）**：原设计的接口全是**点操作**（放/读/删前缀/存在性/移出/移入/取本地路径），而 §4.3 的 GC 有三处扫描——`trash/` 到期、`tmp/` 残留、`releases/**` 孤儿目录——都要"列出某个前缀下的直接子项 + 它们的 mtime 与字节数"，点操作推不出这个能力。故补 `listPrefix()` 与 `StorageEntry`（目录的 `sizeBytes` 是递归累计，GC summary 的"释放字节数"用它）。两个语义要点：**只列一层**（三个调用方要的都是某一层的直接子项，不递归枚举整棵树）；**前缀不存在返回空数组而不是抛错**（GC 每一步都要能基于当前状态推导，第一次跑在空盘上就该是 no-op，见 §4.3 的"幂等且可中断"）。

v1 只实现 `LocalStorageAdapter`。**S3 实现被预留但不实现**：接口里 `localPathOf` 返回 `null` 会让"nginx 直出"退化为"Node 代理流式返回 + 签名 URL（P2）"，这个降级路径在设计上留好，届时不需要改业务代码。

### 1.2 key 规范

```
releases/{projectId}/{prototypeId}/{releaseId}                  ← 版本产物根（不可变）
releases/{projectId}/{prototypeId}/{releaseId}/<相对路径>        ← 产物内的文件
tmp/upload-{taskId}-{random}.zip                                ← 上传临时文件
trash/{yyyyMMdd}/{prototypeId}-{releaseId}-{random}              ← 延迟删除区
manifests/{prototypeId}/{releaseId}.json                         ← 清单副本（不对公网暴露）
```

**为什么用 ID 而不是编码 / 版本号做目录名**：

- 用 `code`（项目编码/原型编码）：它们不可改（D-14）所以也安全，但还要额外做路径注入防护，且编码是"用户可见的业务标识"，一旦将来允许改名（例如另存为新原型）目录就跟着漂。没必要引入这个耦合。
- 用 `version_no`：删掉 v3 后新版本会再叫 v3，目录名会撞上缓存、日志、排查记录，产生歧义。`releaseId` 是全局单调唯一的，永不复用。
- 保留 `projectId` 这一层是**为了运维**：`du -sh releases/*` 能直接看出哪个项目的产物占了多少磁盘，排查容量问题时不必回查数据库。

### 1.3 物理布局

```
{STORAGE_ROOT}/                    （生产 /opt/protohub/storage，开发 ~/protohub-storage）
├── tmp/
├── releases/
│   └── 9/                         （projectId → 项目 CRM系统）
│       ├── 31/                    （prototypeId → 原型 crm-p01）
│       │   └── 77/                （releaseId）← 内容即访问时的站点根，nginx 的 root 指向它
│       │       ├── index.html
│       │       └── assets/…
│       └── 32/                    （prototypeId → 原型 crm-p02）
│           └── 80/
├── manifests/                     ← 文件清单副本，不在 nginx 服务的目录树内
│   └── 31/77.json
└── trash/
```

> **必须核对的一点**：`tmp/` 与 `releases/` **必须在同一挂载点**。因为"发布成功"的最后一步是把目录从 tmp `rename()` 到 releases，`rename` 只有同文件系统内才是原子的；跨挂载点会退化成"拷贝+删除"，期间可能被访问到半个目录。部署检查清单里有 `df` 核对项（部署文档 §8）。

`{STORAGE_ROOT}/releases` 需被 nginx 以只读方式访问。**文件清单副本刻意放在 `manifests/` 而不是版本目录内**：nginx 的 `root` 指向版本目录，因此版本目录里的任何文件都等于对外公开；把运维排查用的清单放在它外面，就**天然不可访问**，不需要靠 deny 规则去堵（deny 规则写漏一次就是信息泄露，不写就没有这个风险）。

## 2. zip 处理流水线（决策 D-10）

### 2.1 阶段划分

```
① validating   同步执行（在 POST /api/releases 请求内，<1s）
② extracting   异步（Worker）
③ postprocess  异步
④ committing   异步
```

| 阶段 | 动作 | 失败表现 |
| --- | --- | --- |
| `validating` | 大小、zip 魔数、条目数、解压总量预估、路径合法性初查、是否含 index.html | **接口直接返回 4xx**，不建任务 |
| `extracting` | 流式解压到 `tmp/work-{taskId}/`，逐条再做一次路径校验（不信任第一次检查） | 任务 `failed`，`UPLOAD_UNSAFE_PATH` 等 |
| `postprocess` | 过滤垃圾文件 → 脱壳 → 入口探测 → 路径改写 → 计算清单与指纹 | 任务 `failed`，`UPLOAD_MISSING_ENTRY` 等 |
| `committing` | `rename` 到 `releases/{projectId}/{prototypeId}/{releaseId}/` → DB 事务写 release + 切指针 + 写事件 | 任务 `failed`，目录留给 GC 清理 |

进度回填：`validating` 0-10、`extracting` 10-60（按已处理字节比例）、`postprocess` 60-90、`committing` 90-100。前端据此画步骤条。

> **这张表的阶段归属在 M3 实施时被收窄了两处（原设计 + 修订说明，偏差 DEV-21、DEV-22）**：
>
> 1. **`UPLOAD_MISSING_ENTRY` 与符号链接拒绝落在 `validating`，不落任务**。第 85 行本来就把"路径合法性初查、是否含 index.html"划在 `validating`，但第 87 行又把 `UPLOAD_MISSING_ENTRY` 写成 `postprocess` 的任务失败——两行在文档内部就是打架的。实施按第 85 行：入口是否存在、条目名是否合法、`S_IFLNK` 属性位（§2.3 第 6 步）都能从 zip 中央目录直接读到，**不必解压就知道这包不合格**；解压出来的只会是垃圾 IO。第 87 行原样保留作为"初查漏掉时"的第二道防线（§2.3 第 4 步的双保险、postprocess 的入口探测仍在实现里，由单测覆盖）。实测读数：`../evil`、`/etc/passwd`、`C:\`、符号链接、6000 条目、单文件 250MB、解压总量超限、高压缩比、非 zip、空包、无 `index.html` 共 11 例全部 `422` 且**库里没有任务行**，>100MB 为 `413`。
> 2. **第 88 行的"目录留给 GC 清理"改成"归属还在自己手上就立刻删"**。GC 定时任务是 M5 交付物，M3 期间失败一次就留一个 `tmp/work-{taskId}/`，实测窗口里能攒到几十个目录；而这一份工作目录已经不可能被复用（重试是从原始包重新解压）。所以 Worker 在判失败且**这一行还归自己**时 `rm -rf` 工作目录，原始包 `tmp/upload-*.zip` 仍按 §4.3 交给 24 小时规则。第 88 行的原写法保留：它现在是"归属被巡检换走时"的行为——那时不能动盘，见 §3.2 的归属令牌。

### 2.2 校验规则与阈值

| 项 | 阈值（env 可调） | 违反时的错误码 |
| --- | --- | --- |
| zip 文件大小 | ≤ `MAX_UPLOAD_BYTES`（默认 104857600 = 100MB） | `UPLOAD_TOO_LARGE` |
| zip 魔数 | 前 4 字节为 `PK\x03\x04`（或空包 `PK\x05\x06`） | `UPLOAD_NOT_ZIP` |
| 条目数 | ≤ `MAX_ENTRIES`（默认 5000） | `UPLOAD_TOO_MANY_ENTRIES` |
| 单文件解压大小 | ≤ `MAX_FILE_BYTES`（默认 209715200 = 200MB） | `UPLOAD_ENTRY_TOO_LARGE` |
| 解压总量 | ≤ `MAX_TOTAL_BYTES`（默认 524288000 = 500MB） | `UPLOAD_UNCOMPRESSED_TOO_LARGE` |
| 压缩比 | `total / source ≤ MAX_RATIO`（默认 1000；同时要求 `total ≤ MAX_TOTAL_BYTES`） | `UPLOAD_SUSPICIOUS_RATIO` |
| 文件数为 0 | — | `UPLOAD_EMPTY` |
| 路径合法性 | 见 §2.3 | `UPLOAD_UNSAFE_PATH` |
| 符号链接 | 一律拒绝 | `UPLOAD_SYMLINK_NOT_ALLOWED` |

**压缩比为什么用 1000 而不是更小的值**：正常情况下 HTML/JS/CSS 文本的压缩比在 3~20 之间；即使极端重复内容也很少超过 200。1000 是"明显异常"的下界，同时真正的保护是 `MAX_TOTAL_BYTES` 这个绝对值上限——**任何 bomb 都绕不过解压总量上限**。压缩比只是提前拒绝省 IO 的辅助手段，不是唯一防线（这点必须在实现时理解清楚，否则容易只做其一）。

### 2.3 路径安全（Zip Slip 防护）

对每个 entry 做如下处理，任一步失败即拒绝整包：

1. 把 `\` 统一替换为 `/`（Windows 打包的 zip 会用反斜杠）。
2. 去掉前导 `./`。
3. 拒绝：以 `/` 开头（绝对路径）、任何一段等于 `..`、含 `\0`、匹配 `^[A-Za-z]:`（Windows 盘符）、任何一段长度 >255 或总长 >1024。
4. **双保险**：计算 `path.resolve(extractRoot, entryName)`，断言结果以 `extractRoot + path.sep` 开头。
5. `yauzl` 打开时设 `validateEntrySizes: true`（若 entry 声明的解压大小与实际不符会报错，也是一种 bomb 防护）。
6. 检查 entry 的 external attributes，若 `S_IFLNK` 位被置则拒绝。

> 为什么第 3 步之后还要第 4 步：`..` 过滤依赖字符串解析的正确性（比如 Unicode 归一化、多重编码），`path.resolve` + 前缀断言是最终兜底，不依赖前面每一步都对。

### 2.4 垃圾文件过滤

解压时直接跳过（不写入磁盘）以下内容，跳过项记入 `warnings`：

```
__MACOSX/          .DS_Store        Thumbs.db
.git/              .svn/            node_modules/
__pycache__/       .idea/           .vscode/
```

这些是"Mac/IDE 打包"最常见的内容，跟着发布出去既浪费磁盘又会让访问记录里多出莫名请求。过滤是**发布时行为**，不改产品经理的源文件。

### 2.5 入口探测与脱壳

```
1. 若根目录存在 index.html → entry = 'index.html'，结束
2. 若根目录不存在 index.html：
   2.1 统计所有 index.html 的路径，选"路径段数最少"的那个作为候选
   2.2 若唯一候选位于**唯一的一个顶层目录**下（如 原型/index.html）→ 脱壳：
       把该顶层目录的内容上提为根，entry = 'index.html'，记警告 UNWRAP_SINGLE_TOP_DIR
   2.3 候选位于多个不同顶层目录下 → 取段数最少的作为 entry（如 原型/index.html），
       不改结构，记警告 MULTI_ENTRY_CANDIDATES 并把候选列表放进报告
3. 完全没有 index.html → 失败 UPLOAD_MISSING_ENTRY
```

脱壳的判定条件刻意收窄到"**唯一**顶层目录且其中**唯一**候选入口"，因为自动上提目录会改变原型内的相对路径基准（`../assets` 之类会失效）。宁可多发一次警告让人看见，也不做激进猜测。

### 2.6 路径改写（决策 D-11）

**要解决的问题**：产品经理的原型里常有 `<script src="/assets/app.js">` 这类**根绝对路径**。平台把站点挂在 `/p/{项目编码}/{原型编码}/` 下，浏览器会把 `/assets/app.js` 解析成 `https://proto.company.com/assets/app.js` → 404 → 白屏。这是"原型打开是白屏"的第一大原因。

**改写规则**

| 文件类型 | 处理方式 | 处理范围 |
| --- | --- | --- |
| `.html` / `.htm` | cheerio 解析，改写属性：`src`、`href`、`srcset`、`poster`、`data-src` | 值以**单个 `/`** 开头且**不以 `//`** 开头（`//cdn...` 是协议相对，属于外链，不动） |
| `.css` | postcss + `postcss-value-parser`，改写 `url(...)` | 同样只处理以单个 `/` 开头的值；`url(data:…)`、`url(http…)`、`url(//…)` 不动 |
| `.js` | **不改** | 见下 |
| 其它 | 不改 | |

改写结果：`/assets/app.js` → `/p/crm/crm-p01/assets/app.js`（前缀由**该原型的**两级编码拼成）。

**三条硬性约束**

1. **不碰 JS**。JS 里的 `fetch('/api/xxx')`、`location.href = '/login'` 是原型的业务行为，正则改写会误伤，而且掩盖掉"这个原型依赖后端"这个事实（该事实应当暴露给使用者和开发，而不是被平台悄悄改掉）。
2. **含 `<base href>` 就不改写**。`<base>` 会改变所有相对路径的基准，此时再做前缀改写可能与 base 叠加产生错误路径。检测到即记 `BASE_TAG_FOUND` 警告，建议产品经理移除 base 后重新导出。
3. **改写失败不阻断发布**。HTML 解析异常等情况下保留原文件并记 `REWRITE_SKIPPED` 警告——宁可原样发出让人看到白屏（可在本地对照排查），也不要改坏内容。

**性能保护**：单文件 >5MB 的 HTML/CSS 跳过改写并记 `REWRITE_TOO_LARGE` 警告（防止畸形大文件拖慢流水线）。

**报告**：改写条数（HTML/CSS 分别计数）写入 `proto_release.manifest.rewrites`，在前端"发布报告"里以人话呈现（**报告里的前缀必须是该原型自己的完整路径**，否则用户照着报告核不对）：

> 已将 12 处根绝对路径改写为 `/p/crm/crm-p01/` 前缀（HTML 12 处，CSS 0 处）
> 检测到 1 个问题：文件 `index.html` 含有 `<base href="/">`，可能影响路径解析 — 建议移除后重新导出

这个"发布报告"是平台可诊断性的核心：用户看到"打开不对"时，第一反应是查这次发布的报告，而不是找开发。

### 2.7 产物指纹与清单

```jsonc
// proto_release.manifest（同时写一份副本到 {STORAGE_ROOT}/manifests/{pid}/{rid}.json）
{
  "entry": "index.html",
  "fileCount": 42,
  "totalBytes": 3145728,
  "files": [ { "p": "index.html", "size": 2048, "sha256": "ab12…" } ],
  "rewrites": { "html": 12, "css": 3 },
  "skipped": [ { "p": "__MACOSX/", "reason": "junk" } ],
  "warnings": [ { "code": "UNWRAP_SINGLE_TOP_DIR", "detail": "已自动上提目录「原型」" } ]
}
```

- `content_hash` = 把所有 `files` 按 `p` 排序后拼成 `p|size|sha256` 行文本，再取 sha256。用途：判断"这次上传的内容与某历史版本是否完全一致"。
- `source_hash` = 上传 zip 的 sha256。用途：判断"同一个包被重复上传"。
- 去重提示：`source_hash` 命中**当前版本** → 返回 `UPLOAD_DUPLICATE_CONTENT`（HTTP 200 + 提示，不建新版本）；前端提供「强制发布」复选框，带上 `force=true` 时照常建新版本。

## 3. 提交与一致性

### 3.0 受理阶段先落库（与接口设计 §5.1 对应）

轻校验通过后、把任务交给 Worker 之前，在**一个事务**里完成：

```
a. 若无项目：INSERT proto_project（code 为空则生成 `p-` + 8 位 base36，冲突重试至多 5 次）
b. 若无原型：INSERT proto_prototype（project_id, code, status='draft'）
      · code 为空则取该项目的下一个序号：`{projectCode}-p{NN}`
        实现：`SELECT max(code) FROM proto_prototype WHERE project_id=? AND code ~ '^{code}-p[0-9]+$'`
        → 解析出序号 +1；并发下由 uk_proto_prototype_code 兜底重试
c. INSERT proto_upload_task（prototype_id, status='pending', temp_key）
```

**为什么在这一步就落库**（而不是等处理完成）：① 编码唯一约束提前生效，两个并发任务抢同一编码时第二个立刻失败，而不是跑完全部解压才冲突；② **发布失败后表单不用重填**——用户可以点「重试」直接复用这个 `draft` 原型和它的 `taskId`；③ 原型详情页能看到"正在发布中"的任务进度浮标。代价是失败会留下一个草稿原型，而草稿本来就允许存在（列表里可见可删）。

### 3.1 处理完成后的提交顺序（先落盘、后写库）

```
1. 解压与后处理全部在 tmp/work-{taskId}/ 完成
2. mv tmp/work-{taskId}/  →  releases/{projectId}/{prototypeId}/{releaseId}/   （同分区 rename，原子）
3. DB 事务：
     a. SELECT id FROM proto_prototype WHERE id = ? FOR UPDATE   （串行化同一原型的取号）
     b. version_no = COALESCE(max(version_no), 0) + 1            （原型内递增）
     c. INSERT proto_release(prototype_id, version_no, ...)
     d. UPDATE proto_prototype SET current_release_id = ?, status='published',
              published_at = now(), first_published_at = COALESCE(first_published_at, now())
     e. INSERT proto_release_event(publish, to_release_id = 新版本)
4. task.status = 'success', progress = 100, release_id = 新版本
```

**注意 `prototype.id` 在受理阶段（§3.0）就已经存在**，所以 `releaseId` 是自增主键、`storage_key` 里的目录名也是预测不出来的——这就是第 2 步的目录路径为什么必须在 `releaseId` 生成之后才能确定。做法：先 `INSERT proto_release` 拿到 id，再 rename，最后回填（或者先取一个 id 序列值再 rename）。**实现时不要图省事用 `max(id)+1` 猜测**，那会在并发下撞车。

**为什么先 rename 再写库**：反过来的话，库写成功而 rename 失败会留下"指针指向不存在的目录"，访问直接 404，且没有任何自愈路径。而先 rename 后写库的最坏情况是"磁盘上有个没被任何记录引用的目录"，这是**可被 GC 自动回收的垃圾**，不会造成用户可见故障。故障模式优先选可自愈的那种。

**§3.1 d 步的状态字段（原设计 + M3 修订说明）**：上面第 d 步原样写的是 `status='published'`。实施时（M3-T8）改为
`status = case when status = 'archived' then status else 'published' end`——原设计会让"往一个已归档的原型上再发一版"
把它静默改回在售，而归档是项目归档联动带进来的用户可见状态（见迭代实施计划 §9.2 DEV-11 的归档语义、
[后端接口设计.md](./后端接口设计.md) §4.3 的归档拒绝）；指针照切、状态不复活，归档是否解除由人显式做。
偏差编号 DEV-16。

### 3.2 并发

| 场景 | 处理 |
| --- | --- |
| 同一原型并发发布 | `SELECT … FOR UPDATE` 锁原型行串行取号；即便漏掉，`uk_proto_release_version (prototype_id, version_no)` 唯一约束会兜底并触发重试（最多 3 次） |
| 同一项目下不同原型并发发布 | **互不影响**：锁的是各自的原型行，版本号序列也各自独立。这是三级模型在实现层的直接收益 |
| 并发创建原型抢同一自动编码 | 两个任务都可能算出 `crm-p03` → `uk_proto_prototype_code` 让其中一个失败 → 重试时重新取号（前端提示语写成"将生成"而非断言具体值，见前端设计 §3.4） |
| 并发发布 + 回滚 | 回滚也走 `FOR UPDATE` 锁同一行，两者串行，最终状态由后提交者决定，事件表如实记录两条 |
| 发布过程中原型/项目被删除 | 原型行被锁，删除等待；若删除先完成，发布在查原型时已是 `deleted_at` 非空 → 任务失败 `PROTO_NOT_FOUND` 并清理 tmp |
| Worker 崩溃 | 任务停留在 `processing` 且 `started_at` 超过 10 分钟 → 启动时与每 5 分钟的巡检把任务重置为 `pending` 并重试一次；第二次仍失败则置 `failed`（`UPLOAD_WORKER_FAILED`） |

> **"重试一次"要成立，回填还必须认得"是哪一次领取在写"（原设计 + M3 修订说明，偏差 DEV-23）**：上面这些行只约定了状态与时间界，没有约定**处理者写回时的匹配条件**。实现按"只认 `status='processing'`"落地时实测出一个洞：巡检把卡住的 `processing` 重投成 `pending`、另一个处理者随即 `claim()` 接管后，**前一个（僵尸）处理者的迟到写入照样匹配得上那一行**——它会把接管者正在跑的任务盖成 `failed`（或盖成自己那次的答案），并且按失败分支 `rm -rf` 掉接管者正在读写的 `tmp/work-{taskId}/`。§3.2 承诺的"重试一次"于是变成"被上一次尝试判死"。
>
> 实现把 `claim()` 时写入的 `started_at` 当**归属令牌**：每条进度与终态写都带 `WHERE id = ? AND started_at = ? AND status = 'processing'` 并返回是否命中；重投会把 `started_at` 清成 `null` 再由新 `claim()` 赋新值，所以旧令牌至少在这一条上匹配不到行。命中 0 行时的行为统一为**停手、不动盘**（工作目录与原始包留给接管者，最终由 §4.3 的 24 小时规则收）。这条已在真库上测：`release-pipeline.spec.ts` 里造出"重投 + 二次认领"后，旧令牌的 `patchProgress/markSuccess/markFailure` 三种写全部返回 false，接管者那一行的 `progress/stage/status/retry_count/started_at` 与 `error_code` 不受影响。

### 3.3 发布任务队列

单实例 v1 用**数据库任务表 + 进程内循环**（不是内存队列）：

- Worker 每 1 秒 `SELECT … WHERE status='pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED`，取到就置 `processing` 并处理。
- 串行处理（`MAX_CONCURRENT_TASKS=1`）：解压是磁盘密集型，并发会拖垮磁盘 IO 并让所有任务都变慢；串行反而让"先提交的先完成"语义清晰。
- 选 `FOR UPDATE SKIP LOCKED` 而不是"内存队列"的目的是**将来直接多开实例就能并行消费**，不需要改代码（对应决策 D-16）。

## 4. 版本、回滚与 GC

### 4.1 版本目录不可变（决策 D-09）

发布新版本 = 新建目录 + 改指针；回滚 = 只改指针。因此：

| 操作 | 磁盘动作 | 生效时延 |
| --- | --- | --- |
| 发布新版本 | 新增 `releases/{pid}/{protoId}/{newRid}/` | 指针更新后立即（HTML 无缓存） |
| 回滚 | 无 | 立即 |
| 原型归档 | 无 | 立即（决策函数返回"该原型已下架"） |
| 项目归档 | 无 | 立即（决策函数返回"所属项目已下架"，其下**所有**原型一起失效） |
| 删除某历史版本 | 标记 + 7 天后物理删除 | 历史版本不可访问，但本来也不是当前版本 |

### 4.2 回滚的实现细节

- 只允许回滚到 `status='ready'` 的版本（`broken`/`deleted` 不行）。
- 回滚也要写 `proto_release_event(rollback, from_release_id = 原当前版本, to_release_id = 目标版本)`，这是"留痕"的依据：谁在什么时候把哪条链接切回过哪一版、为什么。
- `prototype.published_at` 更新为回滚时间（它表示"当前生效版本的生效时间"）；`first_published_at` 不动（表示该原型首次上线时间）。这两个字段语义不同，不要混用。
- **回滚的影响面是"一条链接"**：`prototype.current_release_id` 在原型行上，所以回滚 `crm-p01` 不会碰到 `crm-p02`。这正是为什么要按原型（而不是按项目）持有当前版本指针——如果指针在项目上，"回滚一个原型"在实现上根本表达不出来。

### 4.3 保留与 GC

| 规则 | 值（env） |
| --- | --- |
| 每个原型的当前生效版本 | 永不删除 |
| 每个**原型**保留最近版本数 | `KEEP_RECENT_RELEASES=5` |
| 时间兜底 | 最近 `KEEP_MIN_DAYS=30` 天内的版本一律保留（即使超过数量上限） |
| 物理删除延迟 | `TRASH_TTL_DAYS=7`（先 rename 到 `trash/`，7 天后 `rm -rf`） |
| tmp 残留清理 | 超过 24 小时的 `tmp/**` 一律删除 |
| 孤儿目录清理 | `releases/**` 中 DB 里不存在的 releaseId 且 mtime 超过 1 小时 → 移入 trash（§3.1 引入的垃圾在这里被回收） |
| 任务记录保留 | 90 天 |

> **保留计数必须按原型算，不能按项目算**：一个项目下有 20 个原型，若按项目保留 5 个版本，那每个原型能留的版本会被挤到几乎为零，回滚能力形同虚设。按原型算才是"每个链接都保留自己的 5 个版本"。

**GC 定时任务**（每天 03:30，也在服务启动 5 分钟后跑一次）：

```
① 到期任务记录：delete from proto_upload_task where created_at < now() - 90d
② 到期访问/登录/操作日志：按 180 天保留期删除
③ 可回收版本：逐原型按上述规则选出 releaseId 集合 → status='deleted' + deleted_at=now()
④ 物理删除：trash/ 下超过 7 天的目录 → rm -rf
⑤ 标记 7 天前的 deleted 版本 → 移入 trash（同分区 rename）
⑥ 孤儿目录检测（见上）
⑦ 记录一条 summary 日志：本次删除目录数、释放字节数、当前磁盘余量
```

GC 必须**幂等且可中断**：每一步都基于当前 DB/磁盘状态推导，不依赖上一次执行的游标；中途失败下次重跑能继续。

## 5. 访问鉴权（决策 D-05/D-06/D-07）

### 5.1 决策函数（唯一口径）

```ts
// apps/server/src/access/access.service.ts —— 开发(Node 直出)与生产(nginx auth_request)共用这一个函数
// target 由调用方从请求路径里解析出来（形如 { projectCode: 'crm', prototypeCode: 'crm-p01' }）
export function decideAccess(
  target: { projectCode: string; prototypeCode: string },
  rows: { project: ProjectRow | null; prototype: PrototypeRow | null },
  ctx: { cookie: Record<string, string>; sessionUserId?: string },
): { status: 200 | 401 | 403 | 404; reason?: AccessReason; releaseId?: string } {
  const { project, prototype } = rows;

  // ① 任一层不存在 → 统一 404（不区分"不存在"与"未发布"，避免被用来枚举原型，见 R-9）
  if (!project || project.deleted_at || !prototype || prototype.deleted_at)
    return { status: 404, reason: 'NOT_FOUND' };
  // ② 项目归档 → 其下所有原型都不可访问
  if (project.archived_at) return { status: 403, reason: 'PROJECT_ARCHIVED' };
  // ③ 原型归档
  if (prototype.status === 'archived') return { status: 403, reason: 'PROTOTYPE_ARCHIVED' };
  // ④ 没有生效版本
  if (prototype.status !== 'published' || !prototype.current_release_id)
    return { status: 404, reason: 'NOT_PUBLISHED' };

  switch (prototype.access_mode) {
    case 'public':
      return { status: 200, releaseId: prototype.current_release_id };

    case 'password': {
      // Cookie 名用原型数字 ID，避免两段编码拼接的歧义（见接口设计 §9.2）
      const token = ctx.cookie[`proto_access_p${prototype.id}`];
      if (token && verifyUnlockToken(token, prototype, project))
        return { status: 200, releaseId: prototype.current_release_id };
      return { status: 401, reason: 'NEED_PASSWORD' };
    }

    case 'member': {
      // 注意：成员档只能用 Cookie 判定身份，不能用 Authorization 头，原因见 §5.4
      const uid = ctx.sessionUserId;
      if (!uid) return { status: 403, reason: 'NEED_LOGIN' };
      // 数据范围停在项目层：能看到项目就能看到它下面所有原型（权限模型设计 §6.2）
      if (!isProjectVisibleTo(uid, project)) return { status: 403, reason: 'NO_PERMISSION' };
      return { status: 200, releaseId: prototype.current_release_id };
    }
  }
}
```

**关键点**：`decision` 的输入是"已查好的行"，查询由调用方做（生产环境就是一次按 `(project_id, code)` 唯一索引的 join）。这样决策逻辑是**纯函数**，可以被单测穷举所有组合（3 档策略 × 4 种状态 × 有/无 cookie），而它又是生产放行与开发直出共用的唯一实现。

状态码语义（与后端接口设计 §9.1 一致）：**401 只表示"需要访问密码"，403 表示"需要登录/无权限/已下架"，404 表示"不存在或未发布"**。这样 nginx 侧只需要把 401 映射到密码页、403 到提示页、404 到失效页，映射关系不随业务原因增加而变化。

### 5.2 密码档令牌

```
格式：v1.{policyVersion}.{expEpoch}.{sig}
sig  = base64url(HMAC_SHA256(ACCESS_TOKEN_SECRET, `${项目编码}|${原型编码}|${policyVersion}|${expEpoch}`))
参数：expEpoch = 签发时间 + 24h（秒）
Cookie：Name = proto_access_p{原型ID}
        Path = /p/{项目编码}/{原型编码}   ← 只在该原型路径下携带，不同原型互不干扰
        HttpOnly; SameSite=Lax; Secure(生产)；Max-Age = 86400
```

**校验顺序**：拆 4 段 → 段 2（policyVersion）必须等于**该原型**的 `policy_version` → 段 3（exp）未过期 → 用 `crypto.timingSafeEqual` 重算签名比对。

**签名里带上两级编码的作用**：即使有人在别的路径下拿到了这个 Cookie 值（例如把 Cookie 手工挪到别的原型的请求上，或用 Charles 复制），签名也过不了——因为签名绑定的是这对编码。

**改密码/改访问模式为什么能立即踢掉所有人**：这两类操作都会 `policy_version + 1`，而 `policy_version` 参与签名，因此所有旧令牌签名校验必然失败。这是决策 D-07 的收益——不用维护"已签发令牌表"，也不用等过期。**改一个原型的密码不会影响同项目下其它原型的解锁状态**（`policy_version` 在原型行上）。

### 5.3 门面页

`GET /api/access/gate` 返回一个**自包含的极简 HTML**（内联 CSS、零外部依赖、`Cache-Control: no-store`），因为它的受众可能是**外部客户**，不该把管理台框架暴露给他们。形态：

| 传入 | 页面 |
| --- | --- |
| `code=401` | "该原型需要访问密码" + 密码输入框 + 提交（POST `/api/access/{项目编码}/{原型编码}/unlock`，成功后 `location.reload()`） |
| `code=403&reason=NEED_LOGIN` | "该原型仅限内部成员查看" + 「去登录」按钮（跳 `{PUBLIC_BASE_URL}/auth/login?redirect={原URL}`） |
| `code=403&reason=NO_PERMISSION` | "你没有查看该原型的权限" + 联系管理员提示 |
| `code=403&reason=PROTOTYPE_ARCHIVED` | "该原型已下架" |
| `code=403&reason=PROJECT_ARCHIVED` | "该原型所属项目已下架" |
| `code=404` | "链接无效或已失效"（**不区分**"不存在"与"未发布"，避免被用来枚举编码） |
| `code=403` 而 `reason` 缺失/不认；`code=401` 配上一个不该出现的原因 | "该原型暂时无法访问"（兜底形态，见下方修订说明第 2 点） |
| `code` 缺失或不等于 `401`/`403`/`404` | 与 `code=404` 同一页 |

> 页面**不显示项目名、原型名等任何业务信息**（只显示"该原型"这类中性措辞）：门面页是公开可达的，任何回显都会变成"输入编码即可探测该原型是否存在及其名称"的信息泄露源。这与 §5.1 的①统一 404 是同一件事的两面。

> **原设计 + 修订说明（M4-T6，计划 §9.2 DEV-30）**：上表原本只给"六种传入 → 六种页面"的一一对应，实现时补了三件事，都不改变对外契约：
>
> 1. **入参逐个验证后再用**。`project`/`prototype` 必须过 `packages/shared` 的 `CODE_RULE`（与 §5.2 解锁接口、`/api/access/check` 的 URI 解析同一份判定），因为它们会被拼进密码表单的 `action`；`code` 必须是 `401|403|404`，`reason` 必须在 `ACCESS_REASONS` 里。**401 但编码不合法时不给密码框**，退化成"链接无效"——否则就是一个提交不出去的输入框（表单目标本身就是那两段编码）。
> 2. **多一个兜底形态**：403 而原因不在那四个之内（含缺失、拼错）时，页面只说"该原型暂时无法访问"。不猜形态是因为猜错会把"你没权限"的人引导去登录，而登录后仍然是 403，人就卡在两个页面之间循环。
> 3. **`from` 只接受站内 `/p/` 路径**：带 scheme 的绝对地址、协议相对地址（`//evil/x`，浏览器视为另一个站）、含 `..` 的路径（`/p/../admin` 会被归一化成 `/admin`）、管理台自身路径、超过 512 字符一律丢弃，只留 `/auth/login` 本身。这个参数最终会进 `{PUBLIC_BASE_URL}/auth/login?redirect=`，是本页面上唯一的开放重定向风险点。
>
> **文案（M4 回写项，以 `apps/server/src/modules/access/gate-page.ts` 的 `COPY` 表为准）**：主标题「需要访问密码 / 需要登录 / 没有访问权限 / 原型已下架 / 项目已下架 / 链接无效 / 暂时无法访问」，正文逐字为 §5.3 表中引号内那句，补充说明分别是"密码由原型的所有者提供。输入正确后一天内不必再输。""登录后即可访问。如果登录以后仍然打不开，说明你还不是该项目的成员。""该原型只对项目成员开放，请联系原型的所有者把你加入项目。""所有者把它撤下了；如果确有需要，请联系他重新发布。""项目下架期间其下所有原型都不可访问，恢复项目后即可打开。""可能是原型已被删除、编码写错，或这条链接还没有发布过内容。""请稍后重试；如果一直打不开，请把这条链接反馈给原型的所有者。"。原表里"联系**管理员**提示"改为"联系原型的**所有者**"——NO_PERMISSION 的唯一出路是被拉进项目，而只有所有者能做这件事（管理员在管理台里，外部访客没有管理员可找）。
>
> **状态码**：这个接口自己恒返回 200，对外的 401/403/404 由 nginx `error_page` 保留原响应状态码后再取它（部署方案 §5）。这样"直接打开 `/api/access/gate?code=401&...` 看某一形态"成为可能，Gate G9 的逐形态核对就是这么做的。

### 5.4 ⚠️ 成员档必须用 Cookie 判定（设计修正）

**事实**：浏览器发起的**顶层导航**（用户在地址栏/微信里点开链接、或新标签打开）**不会携带 `Authorization` 头**——这个头只由 JS 里的 fetch/XHR 主动设置。原型的静态资源请求同理（`<script src>`、`<img>` 都是浏览器原生发起的）。

**推论**：member 档如果只在 `/api/access/check` 里读 `Authorization: Bearer`，**永远判定不到登录态**，所有人都会被拦（这是最容易出错、也最难在联调时发现的一处）。

**方案**：登录时除 refresh Cookie 外，再下发一个**会话 Cookie 供静态访问判定使用**：

| Cookie | 值 | Path | 属性 | 用途 |
| --- | --- | --- | --- | --- |
| `proto_refresh` | refreshToken | `/api/auth` | HttpOnly, SameSite=Lax, Max-Age 7d | 刷新 accessToken（vben 约定） |
| `proto_sess` | 签名载荷 `v1.{userId}.{tokenVersion}.{exp}.{sig}` | `/` | HttpOnly, SameSite=Lax, Max-Age 7d | 供 `/api/access/check` 判定 member 档身份 |

- `/api/access/check` 只读 `proto_sess`（不读 Authorization），并在校验时比对 `token_version`，因此"改密码/被禁用"依然即时生效。
- `/auth/refresh` 时一并轮转 `proto_sess`；`/auth/logout` 清除两者。
- **SameSite=Lax 的已知限制**：如果原型被嵌在第三方站点的 `<iframe>` 里，Lax 会导致 `proto_sess` 不被发送 → member 档在 iframe 中不可用。一期接受这个限制（内部平台的原型链接通常是直接点开），并在门面页提示"请在浏览器新标签中打开"。若将来确需 iframe 嵌入，改为 `SameSite=None; Secure`（届时必须重新评估 CSRF 风险，因为 `/api/access/check` 会变成可被跨站携带凭据的只读接口）。

### 5.5 nginx 如何知道要服务哪个版本目录

nginx 不能查数据库，所以由 `auth_request` 的**响应头**把答案带回来：

```
/api/access/check 在 200 时返回：
  X-Proto-Release-Dir: releases/9/31/77      （项目/原型/版本 三级 ID）
  X-Trace-Id: …

nginx:
  map $upstream_http_x_proto_release_dir $proto_release_dir {
      ~^releases/[0-9]+/[0-9]+/[0-9]+$  $upstream_http_x_proto_release_dir;   # 形状白名单
      default                          "_invalid";                            # 异常值落到不存在目录
  }
  （然后在 root 里使用 $proto_release_dir）
```

**三级 ID 与白名单 map 都必须保留**：直接写 `root /opt/protohub/storage/$upstream_http_x_proto_release_dir` 时，一旦该响应头缺失（后端 bug、非 200 响应残留），`root` 会退化成 `/opt/protohub/storage/`，请求就能命中 `manifests/` 与 `trash/`——这是一次目录泄露。部署文档 §5.1 把这条列为"最容易被后续改动破坏的一处"。

403/401 时也返回一个头 `X-Proto-Reason: NEED_LOGIN|NEED_PASSWORD|…`，由 nginx 透传给门面页，让门面页显示对应形态。完整配置见 [部署与运维方案.md](./部署与运维方案.md) §5。

## 6. 访问记录（写入策略）

记录粒度直接决定性能，规则如下（对应平台设计方案 R-8）：

| 记录 | 是否入库 | 说明 |
| --- | --- | --- |
| 入口文档请求（`/p/{项目}/{原型}/`、`.../index.html`） | ✓ `ok` | 这是"有人访问了这个原型"的真实信号 |
| 被拒请求（401/403/404） | ✓ 对应 result | 用于发现"有人拿到链接但被拦住"（例如密码没发对） |
| 编码不存在 / 原型已删除的请求 | ✓ `not_found` | 此时 `prototype_id` 为空，靠 `route_key`（`crm/crm-p01`）定位。**这类记录是"旧链接还在被人用"的直接证据**，也是 `invalidPv` 指标的数据源 |
| 非入口的资源请求且成功 | ✗ | 一个原型 40 个资源，全记会让访问量虚高 40 倍 |
| 非入口的资源请求且 404 | ✓ `not_found` | **这是"白屏"的关键线索**：路径改写没覆盖到、资源缺失，都会在这里出现 |
| 静态资源 200 | ✗ | — |

**异步批量写入**：决策得出后把记录塞进进程内缓冲（上限 500 条或 2 秒），批量 `insert`。写失败只落本地日志文件，**绝不影响文件返回**（静态访问的可用性优先于统计完整性）。

**UA 解析**：用轻量库（`ua-parser-js` 或自写正则）抽出 browser/os/device；识别常见爬虫标记 `is_bot`（UA 含 bot/crawler/spider/curl/wget/headless）。`is_bot` 的请求**不计入 UV**，但保留记录（用于发现"链接被放到公开群被爬"这类情况）。

**IP 处理**：`X-Real-IP` → PG `inet`。注意 `X-Forwarded-For` 可伪造，因此**以 nginx 设置的 `X-Real-IP`（`$remote_addr`）为准**；若将来前面还有一层 CDN，需要改为信任 CDN 回源头并加白名单，不能无条件取 XFF 第一段。

### 6.1 记录点的分布（原设计 + 修订说明，M4-T9 / 计划 §9.2 DEV-33）

**原设计**：上面那张表按"请求结果"规定记与不记，读起来像有一个统一的记录器在请求结束后看一眼状态码。**实际有三个调用点、两种部署形态**，表本身不足以决定"同一次访问落几条记录"。修订如下（表的六行判据不变）：

| 记录点 | 何时用 | 记哪些 | 不记哪些 |
| --- | --- | --- | --- |
| `/api/access/check`（nginx `auth_request` 那一跳） | 线上形态的每一次 `/p/…` 请求 | 入口 `ok`、全部被拒（`denied_401`/`denied_403`/入口 `not_found`） | **非入口的 404**（这一跳不知道文件在不在，留给门面页） |
| `/api/access/gate`（`error_page` 转进来） | 线上形态下 nginx 自己发现静态文件缺失 | **只有**"`code=404` 且 `from` 可解析且非入口"这一种 | 其余全部（401/403/入口 404 已由 `check` 记过，两处都记就是同一次访问两条） |
| Node 直出路由（`SERVE_STATIC=node`） | 开发期与单机部署，没有 nginx 那一跳 | **全记**（含点文件 `denied_403`） | 与另两点同规则 |

三点共用 `accesslog/record-policy.ts` 的 `accessLogResultOf({isEntry, status})` 一份判定，没有任何一处自己写"这种情况记不记"。

**`301`/`304`/`500` 三处都不记**，且 301 不需要写规则：nginx 的补尾斜杠发生在 rewrite 阶段，永远走不到 `auth_request`。`304` 是同一次访问的重复信号，`500` 时连"访问的是什么"都不确定，写进去只会污染 PV。

**门面页因此不再是无副作用的渲染接口**（这是对原设计的一处实质改动，代价说清楚）：人肉打开 `?code=404&from=/p/x/y/missing.js` 看形态也会往统计里加一行 `not_found`。不这样做的替代方案是放弃机制 §6 表里"非入口资源 404 是白屏的关键线索"这一行——那行在线下就没有落点。**`from` 只用于补记这一条记录，不参与页面渲染、不做跳转**。

**这一条记录没有 `user_id`**：Cookie 在 `error_page` 那一跳是透传的（`proxy-common.conf` 不清 `Cookie`），不做身份解析是取舍——认出登录者要验签 + 查用户表 + 比项目数据范围三次查询，而这条记录的价值在"哪个文件缺失"。有身份的两类行（入口成功、入口被拒）仍由 `check` 记全。

**缓冲的三条补规则**（原文只写了"上限 500 条或 2 秒""写失败只落本地日志"）：
- 一次 `createMany` 最多 **500 行**，剩下的行**重新排一个 2 秒窗口**再写。突发（一次发布被一批爬虫打）在同一轮事件循环里就能塞进远超 500 条，整包下发会把单条 SQL 的参数个数推到几万；而触发写入的那次 `enqueue` 已经把定时器清掉，不重排的话余下的行会一直躺到下一条记录进来或进程退出。
- 待写行数硬上限 **2000**，超了**丢新到的**并每丢 100 条 warn 一次。没有上限就是数据库故障时把缓冲堆到 OOM；丢弃加计数比阻塞静态访问诚实（本文开头那句"静态访问的可用性优先于统计完整性"的具体形态）。
- 批次**串行**（不同并发各发一条 `createMany` 会让写入顺序与到达顺序不一致，日志的"最后一次访问"就成了随机值）、写失败**丢弃不重试**、`onModuleDestroy` 冲一次尾、定时器 `unref()`（否则测试与优雅退出会被它吊住）。

**`is_bot` 与 UV 的口径落点**：爬虫识别在 `ua-parser.ts`（自写正则，走原文允许的"或自写正则"这一支——`ua-parser-js` 不在计划 §3.2 的依赖白名单），token 命中 `bot|crawler|spider|curl|wget|headless` 时 `device` 直接给 `bot` 并优先于设备类型判定。`os` 里 **`macOS` 不带版本号**：Mac 的 UA 里根本没有系统版本段（`Windows NT 10.0` 那种写法才有），宁可不给也不猜。

**入库前的字段收敛**：`path` 只取 `?`/`#` 之前的部分（查询串可能带临时口令，统计只需要"哪个文件"）、`created_at` 用**请求时刻**而不是写入时刻（批量最多滞后 2 秒，跨过日界线会把访问算到第二天）、超列宽的字符串裁剪而不报错、id 解析不出纯数字一律按空处理。

## 7. 缓存策略（决策 D-12）

| 资源 | 响应头 | 理由 |
| --- | --- | --- |
| HTML（`.html`/`.htm`，以及目录默认文档） | `Cache-Control: no-store` | 切版本、改密码、下架必须**下次刷新就生效**；HTML 体积小，省这点带宽不划算 |
| 其它静态资源（js/css/图片/字体） | `Cache-Control: no-cache` + nginx 自动生成的 `ETag`/`Last-Modified` | 每次带条件请求：内容没变返回 304（极快），内容变立刻拿到新的 |
| 点文件（版本目录里若有 `.` 开头文件） | deny（不对外提供） | 清单副本已移出该目录树（§1.3），此条只作兜底 |
| 门面页 `/api/access/gate` | `no-store` | |
| API 响应 | `no-store`（默认） | 权限与数据随时变 |

**判据作用在原始 URI 上**（不是 rewrite 之后的文件路径）：nginx 用 `map $request_uri …`，Node 直出用 `isHtmlUri(request.url)`，两边同形。所以"目录默认文档"这一行靠的是**以 `/` 结尾**这一条，而不是把它解析成 `index.html`——`/p/{项目}/{原型}/` 这条被分享与收藏的链接必须和 `/index.html` 拿到同一个 `no-store`。

**为什么不用"资源长缓存 + 版本号进 URL"**：把版本号（`/p/crm/crm-p01/v3/assets/app.js`）写进 URL 会破坏"链接稳定"这一核心承诺——发出去的链接必须长期有效、内容可被更新。**稳定性优先**，代价是每次访问多一轮 304 协商（原型通常 40 个资源以内，且现代浏览器并行 6 连接，实测开销在百毫秒级）。

**折中开关（P1）**：为资源体积大（>10MB）且访问频繁的**原型**提供原型级开关，把资源改为 `max-age=300`，代价是切版后最多 5 分钟内新旧不一致。默认关闭。

**brotli/gzip**：`text/html`、`text/css`、`application/javascript`、`application/json`、`image/svg+xml` 开启压缩（见部署文档 §5）。原型里的 HTML/CSS/JS 压缩收益明显。

### 7.1 为什么鉴权决策不缓存

每次静态资源请求都会触发一次 `auth_request`。**不缓存决策结果**是刻意的：缓存 60 秒会让"改密码/下架"在最多 60 秒内不生效，而这是安全相关的承诺（成功标准里写了 ≤1s）。代价是每次请求多一次本机 HTTP 往返（127.0.0.1，约 0.3ms）+ 一次 `(project_id, code)` 唯一索引查询（约 0.1ms）——相对静态文件返回可以忽略。

为了让这个开销保持可忽略，`/api/access/check` 的实现有两条硬约束：**禁止联表统计**、**禁止在此写访问日志的同步 DB 插入**（日志走异步批量缓冲，见 §6）。

## 8. 错误码与可诊断性

### 8.1 发布失败的错误码

完整错误码表见 [后端接口设计.md](./后端接口设计.md) §8（唯一权威）。本文只补充**面向使用者的"下一步做什么"**原则：错误码是人话的补充，不是替代品——界面必须展示 `error`（如"压缩包内含非法路径，已拒绝"），错误码以小字形式放在旁边供报障时复制。

### 8.2 失败与异常的可查性（硬要求）

| 信息 | 存放位置 | 界面入口 |
| --- | --- | --- |
| 每次发布的结果（含警告与改写条数） | `proto_release.manifest` + `{STORAGE_ROOT}/manifests/{pid}/{rid}.json` | 项目详情 → 版本记录 → 该版本 → 发布报告 |
| 发布失败原因 | `proto_upload_task.error_code/error_message` | 上传抽屉的失败态 + 右下角任务浮层（原「上传发布页」入口已于 2026-10-07 随 DEV-42 移除） |
| 请求链路 | `X-Trace-Id` 响应头 ↔ 服务端 JSON 日志（pino） | 报障时让用户提供该 id |
| 访问被拒的原因 | `proto_access_log.result` + `release_event` | 访问记录页按"结果"筛选 |
| 管理操作留痕 | `sys_oper_log`（含变更前后差异） | 设置 → 操作日志 |

**原则**：任何一次"用户觉得不对"的场景，都要能在界面里查到一条记录**指向具体原因**，而不是只能靠登服务器翻日志。这也是任务表与事件表必须落库、而不是只在内存/文件里维护的原因。

## 9. 性能与容量

| 项 | 设计 | 说明 |
| --- | --- | --- |
| 上传内存占用 | 流式落盘（Fastify multipart → 文件流），不缓存整个包 | 100MB 包不占 100MB 内存 |
| 解压内存占用 | yauzl 流式 + 顺序写文件 | 与包大小无关 |
| 解压并发 | 串行（`MAX_CONCURRENT_TASKS=1`） | 磁盘 IO 是瓶颈，并发只会让所有任务都慢 |
| 静态访问 | nginx 直出（`sendfile`/`aio`） | 不经过 Node，Node 只处理一次鉴权 |
| 鉴权开销 | 单次 <1ms（本机回环 + 唯一索引查询） | 见 §7.1 |
| 访问记录写入 | 异步批量（500 条 / 2 秒） | 不阻塞返回 |
| 磁盘增长模型 | `原型数 × 每个原型保留版本数 × 平均包体积` | 例：一个项目 6 个原型 × 5 版本 × 平均 8MB ≈ 240MB；10 个项目约 2.4GB。含 trash 缓冲建议预留 ≥20GB |
| 单实例上限 | 单机磁盘与带宽决定，Node 本身不是瓶颈（静态直出不经过它） | 需要横向扩展时：多开实例 + 共享 PG + 共享对象存储（P2） |

> **磁盘模型按原型算，不按项目算**——这一点与 §4.3 的保留策略同源。一个项目下有 20 个原型时，产物总量是 `20 × 5 × 包体积`，不是 `5 × 包体积`；容量规划若用"项目数 × 版本数"会低估一个数量级（对应平台设计方案 R-10：项目下原型过多是需要被看见的信号）。
