# 后端接口设计

> 状态：设计待评审 ｜ 日期：2026-10-06 ｜ 关联：权限模型设计.md §3/§5、数据库设计.md、前端设计.md

服务端：NestJS 11 + Fastify。**本文是 API 契约的唯一权威**。契约类型统一定义在 `packages/shared/src/api-types/`，前端直接引用，避免字段对不上。

## 1. 通用约定

### 1.1 路径与前缀

| 项 | 约定 |
| --- | --- |
| baseURL | `/api`（前端 `VITE_GLOB_API_URL=/api`，生产由 nginx 反代到 Node） |
| 业务路径 | 直接跟在 `/api` 后，形如 `/api/projects`、`/api/system/users`。**暂不做 `/v1` 版本段**，将来需要时改 `VITE_GLOB_API_URL` 即可 |
| 方法语义 | GET 查询、POST 创建/动作、PUT 全量更新、PATCH 局部更新、DELETE 删除 |
| 命名 | 路径用复数名词（`/projects`），动作用子路径（`/projects/{id}/rollback`），不用动词当资源名 |
| 时间 | 一律 ISO 8601 带时区，如 `2026-10-06T14:30:00+08:00`；前端不解析字符串拼时间 |
| ID | 字符串形式的数字（避免 JS 精度问题；数据库是 bigint，序列化时转 string） |

### 1.2 统一响应体

所有接口（**唯一例外：`/auth/refresh`，见 §2.2**）使用同一包装：

```jsonc
// 成功
{ "code": 0, "data": { /* 业务数据 */ }, "error": null, "message": "ok" }

// 失败（同时返回非 2xx 的 HTTP 状态码）
{
  "code": -1,
  "data": null,
  "error": "编码已被占用，请换一个",   // 给人看的文案（前端优先取这个字段展示）
  "message": "编码已被占用，请换一个",
  "errorCode": "PROTO_SLUG_DUPLICATED"      // 给机器/排障用的稳定错误码
}
```

**为什么同时给 `error` 和 `errorCode`**：vben 前端 `errorMessageResponseInterceptor` 的取值顺序是 `responseData.error ?? responseData.message`，因此把**人话放进 `error`** 就能零改动地正确提示；同时用一个额外的 `errorCode` 字段承载稳定错误码，供前端做分支逻辑（例如发布失败时展示"查看发布报告"按钮）与后端排障。不要把人话和错误码混在同一个字段里。

### 1.3 分页约定（与 vben 表格对齐）

**请求**（query）：`page`（从 1 开始）、`pageSize`（默认 20，上限 200）、`sortBy`、`sortOrder`（`asc`/`desc`），其余业务筛选字段平铺。

**响应**：

```jsonc
{ "code": 0, "data": { "items": [ /* ... */ ], "total": 137 }, "error": null, "message": "ok" }
```

### 1.4 状态码语义

| HTTP | 何时返回 | `errorCode` 前缀 |
| --- | --- | --- |
| 200 | 业务成功 | — |
| 400 | 参数校验失败、业务规则拒绝（如编码格式非法、不能删除最后一个超管） | `*_INVALID` / `*_RULE_*` |
| 401 | 未登录、accessToken 无效/过期/被撤销（禁用、改密后） | `AUTH_*` |
| 403 | 已登录但**权限不足**或数据范围外 | `AUTH_FORBIDDEN` / `PROTO_NOT_ACCESSIBLE` |
| 404 | 资源不存在 | `*_NOT_FOUND` |
| 409 | 并发冲突（重复发布抢版本号、编码并发占用） | `*_CONFLICT` |
| 413 | 上传文件超限 | `UPLOAD_TOO_LARGE` |
| 422 | 上传的 zip 内容不合法（见 §8 错误码表） | `UPLOAD_*` |
| 429 | 触发限速（解锁接口、登录） | `RATE_LIMITED` |
| 500 | 未预期异常（不暴露堆栈，返回 traceId） | `INTERNAL_ERROR` |

> **易错点**：token 过期必须是 401，权限不足必须是 403。写反会导致前端该刷新时不刷新、不该登出时被登出（vben 只对 401 触发 refresh）。

> **201 只给"真的创建了资源"（M3-T9 实施补记）**：`POST` 创建（项目/原型/用户/角色/菜单）返回 201；`POST` 形态的**状态变更**——归档与恢复上架（4.1.7/4.1.8、4.3.7/4.3.8）、回滚（5.5）——一律 **200**，响应体仍是更新后的资源；发布受理按 §5.1 固定 202。本节此前没写死这一条，实现按 Nest 对 POST 的默认值落了 201，M3-T9 实测时逐条纠正（`@HttpCode(HttpStatus.OK)`），属实现口径补齐而非设计变更。

> **400 的边界（M2 实施补记，见迭代实施计划 §9.2 DEV-9）**：本表的 400 只留给"参数不合法/业务规则拒绝"。无 body 的 POST/DELETE（登出、归档/恢复、删项目）天然带 `content-type: application/json`，而 Nest/Fastify 的默认 JSON 解析器会因"JSON 类型 + 空体"直接抛 400——那与业务无关。服务端已在 `apps/server/src/main.ts` 注册自定义 `application/json` 解析器：空体按"没有 body"放行（`undefined`），非空体仍 `JSON.parse`。所有 DTO 都是 `.strict()`，多出来的键（含 `__proto__`）在参数校验层就被拒，解析行为不另起一套。

### 1.5 其他约定

| 项 | 约定 |
| --- | --- |
| 幂等 | 上传发布接口用 `Idempotency-Key`（前端生成 UUID）防重复提交；重复键在 10 分钟内直接返回首次结果 |
| 追踪 | 响应头回传 `X-Trace-Id`，与日志中的 traceId 一致，报障时让用户提供该值 |
| 分页上限 | `pageSize > 200` 直接夹取为 200，不报错 |
| 空值 | 可选字段缺省返回 `null`，不返回 `undefined`（JSON 序列化会丢字段，导致前端类型不符） |

## 2. 认证与用户信息（vben 框架强依赖，实现必须与实测行为一致）

这一组接口是 vben 前端框架**写死调用**的，路径、请求体字段、返回结构都不能改（否则登录流程直接跑不通）。

### 2.1 POST `/api/auth/login`

- 权限：无需登录
- 请求：`{ "username": "admin", "password": "******" }`
- 响应 `data`：

```jsonc
{
  "accessToken": "eyJhbGciOi...",     // vben 从这里取 token，字段名必须是 accessToken
  "userId": "1", "username": "admin", "realName": "张三", "avatar": null,
  "roles": ["super_admin"],
  "homePath": "/dashboard/workspace"  // 登录后跳转页；vben 优先用它
}
```
- 副作用：两个 `Set-Cookie`
  - `proto_refresh=...; HttpOnly; Path=/api/auth; SameSite=Lax; Max-Age=604800`（生产加 `Secure`）
  - `proto_sess=...; HttpOnly; Path=/; SameSite=Lax; Max-Age=604800`（生产加 `Secure`）——供原型 member 档访问判定使用，见 §9.1 与发布机制文档 §5.4
- 失败：用户不存在或密码错 → **401**，`errorCode=AUTH_BAD_CREDENTIALS`（不要用 403：vben 会把 403 当权限不足提示，且不会触发任何刷新逻辑）
- 其它：写 `sys_login_log`；连续失败 5 次锁定 15 分钟（按 `username + ip` 计数，内存 + 落库）；被禁用用户 → 401 `AUTH_DISABLED`

### 2.2 POST `/api/auth/refresh` ⚠️ 特殊

- 权限：无（凭 Cookie 中的 refreshToken）
- 请求：无 body；浏览器自动带 `proto_refresh` Cookie
- **响应：HTTP 200，响应体是裸字符串（新的 accessToken），不是统一包装**

```
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```
- 副作用：轮转 `proto_refresh` 与 `proto_sess` 两个 Cookie
- 失败：无 Cookie / 校验失败 / 用户已禁用 → **403** + 统一错误包装（`AUTH_REFRESH_INVALID`），并 `Set-Cookie` 清除 Cookie

> **为什么必须是裸字符串**：vben 的 `refreshTokenApi` 用的是不挂默认响应拦截器的 `baseRequestClient`（`responseReturn: 'raw'`），代码是 `const resp = await refreshTokenApi(); accessStore.setAccessToken(resp.data)`。若返回 `{code,data}` 包装，`resp.data` 会是整个对象，随后所有请求头变成 `Authorization: Bearer [object Object]`。（依据：`preset-interceptors.ts`、`packages/effects/request/src/request-client/request-client.ts` 默认 `responseReturn: 'raw'`）

### 2.3 POST `/api/auth/logout`

- 权限：需登录
- 请求：无 body
- 响应：`data: null`
- 副作用：清 `proto_refresh` 与 `proto_sess`；写 `sys_login_log(login_type='logout')`

### 2.4 GET `/api/auth/codes`

- 权限：需登录
- 响应 `data`：`["dashboard:workspace:view", "proto:project:list", ...]`（该用户全部权限码的扁平数组）
- 说明：`super_admin` 返回全部权限码（不是空数组），便于前端按钮统一用权限码判断，避免"超管看不到按钮"这类问题

### 2.5 GET `/api/user/info`

- 权限：需登录
- 响应 `data`：必须包含 vben 需要的字段

```jsonc
{
  "userId": "1", "username": "admin", "realName": "张三",
  "avatar": null, "desc": "平台管理员",
  "roles": ["super_admin"],                  // 角色 code 数组，vben 用于 hasAccessByRoles
  "homePath": "/dashboard/workspace",
  "email": "zhang@company.com", "phone": null,
  "dataScope": "all",
  "forcePasswordChange": false
}
```

### 2.6 GET `/api/menu/all`

- 权限：需登录
- 响应 `data`：**路由树**（不是数据库菜单表原样），只返回当前用户有权访问的节点，且 `status=1`、`type != 'button'`

```jsonc
[
  {
    "name": "ProtoProject",
    "path": "/proto/project",
    "component": "/proto/project/index",     // 相对 apps/admin/src/views 的路径
    "meta": { "title": "原型项目", "icon": "lucide:folder-code", "order": 2, "affixTab": false }
  }
]
```
- 字段映射规则：数据库 `sys_menu` → `meta`：`title→meta.title`、`icon→meta.icon`、`sort→meta.order`、`keep_alive→meta.keepAlive`、`hide_in_menu→meta.hideInMenu`、`menu_visible_with_forbidden→meta.menuVisibleWithForbidden`、`authority`（逗号分隔）→`meta.authority: string[]`
- `type` 映射：`catalog`/`menu` → 普通路由；`embedded` 与 `link` 时 `component` 固定为 `IFrameView`，并把 `iframe_src`/`link_url` 放进 `meta.iframeSrc`/`meta.link`
- **不返回** `type='button'` 的节点：按钮权限走 `/auth/codes`，避免前端菜单树里出现空节点
- 校验提醒：`component` 必须能匹配到 `apps/admin/src/views/**/*.vue`，否则前端控制台会打印 `route component is invalid` 并渲染 404。排障先看这条日志。

### 2.7 PUT `/api/user/profile`

- 权限：需登录（改自己）
- 请求：`{ "realName": "张三", "email": "...", "phone": "...", "avatar": "..." }`（仅这四个字段可改）
- 响应：`data` 同 `/user/info`

### 2.8 PUT `/api/user/password`

- 权限：需登录
- 请求：`{ "oldPassword": "...", "newPassword": "..." }`
- 响应：`data: null`
- 副作用：`token_version + 1`（其它设备的 accessToken 与 `proto_sess` 全部失效）、`force_password_change = false`、清当前 `proto_refresh`/`proto_sess` 并提示前端重新登录
- 校验：新密码 ≥8 位且含大小写/数字/符号中至少 3 类；不得与前 3 次历史密码相同（`sys_user` 加 `password_history` 不需建表，用 `sys_oper_log.detail` 里的 hash 不便——因此**一期只做强度校验，不做历史密码比对**，记入 P1）

## 3. 工作台

### 3.1 GET `/api/dashboard/overview`

- 权限：`dashboard:workspace:view`
- 响应 `data`：

```jsonc
{
  "projectStats": { "total": 24, "published": 19, "draft": 3, "archived": 2 },
  "prototypeStats": { "total": 86, "published": 71, "draft": 12, "archived": 3 },
  "releaseStats": { "thisWeek": 7, "today": 2 },
  "visitStats": { "today": 152, "last7d": 903, "previous7d": 858, "uvLast7d": 118, "deniedLast7d": 26 },
  "recentPrototypes": [ { "id": "31", "name": "登录页演示", "code": "crm-p01",
                          "projectId": "9", "projectName": "CRM系统",
                          "accessUrl": "https://proto.company.com/p/crm/crm-p01",
                          "status": "published", "updatedAt": "...", "visitsLast7d": 88 } ],
  "recentEvents": [ { "id": "41", "projectName": "CRM系统", "prototypeName": "登录页演示",
                      "prototypeCode": "crm-p01", "eventType": "rollback",
                      "operatorName": "张三", "createdAt": "...", "reason": "新版样式被否" } ]
}
```
- 说明：`recentPrototypes` 取最近更新的 5 个**原型**（不是项目——每天在动的是原型）；`recentEvents` 取最近 10 条；全部**受数据权限过滤**（只看得到自己范围内的项目及其原型）
- 窗口口径：`today` / `last7d` / `previous7d` / `uvLast7d` / `deniedLast7d` 一律按 §6.2 的**服务器本地日历日**窗口算（`last7d` = 含今天的最近 7 个日历日，`previous7d` = 再往前 7 个日历日），这样工作台与访问记录页对同一件事给同一个数。`recentPrototypes[].visitsLast7d` 与项目列表那列同源（滚动 7×24h，见计划 §9.2 DEV-38 的对照说明）。
- 发布数口径（M5-T1，计划 §9.2 DEV-38）：`releaseStats.thisWeek` / `today` 数的是 **`proto_release` 行**（`deletedAt: null`，状态不再筛——`broken` 版本在 §5.4 列表里照样展示，这里同样算一次发布），不是 `publish` 事件。原因是回滚（§5.5）、重新上架与标记删除（§5.6）只往 `proto_release_event` 补事件、不补版本行，而卡片那句「本周发布次数」问的是**新落地的版本**。窗口与上面同一条尺子：`thisWeek` = 本地日历周（**周一起点**）至今，`today` = 本地日界至今，两处共用 `common/calendar-window.ts` 的同一个算术。
- 修订说明（M5-T1，计划 §9.2 DEV-38）：`visitStats` 原设计只有四个字段，本节漏了前端设计 §3.1 那句「近 7 天访问量（**含环比小字**）」所需的对照量——没有 `previous7d` 界面就只能画一条没有基准的曲线。因此补这一个字段（不改已有四个的含义），环比由前端算 `(last7d - previous7d) / previous7d`、`previous7d = 0` 时不显示百分比而不是显示 100%。

## 4. 项目与原型

层级：项目（容器）→ 原型（**一条可独立分享的链接**）→ 版本。接口按层级分开，不做"项目接口顺带返回全部原型明细"这种混合形态——列表页要的是每行摘要，详情页要的是完整对象，混在一起会让响应体随着原型数量膨胀。

### 4.1 项目

| # | 方法 & 路径 | 权限码 | 说明 |
| --- | --- | --- | --- |
| 4.1.1 | `GET /api/projects` | `proto:project:list` | 分页列表，支持 `keyword`（名称/编码模糊）、`status`（`archived`/`published`/`draft` 派生值）、`sortBy` |
| 4.1.2 | `GET /api/projects/check-code` | `proto:project:create` | 项目编码可用性校验，query `code`，返回 `{ available, reason, suggestion }` |
| 4.1.3 | `POST /api/projects` | `proto:project:create` | 创建项目（`code` 可省略，服务端自动生成） |
| 4.1.4 | `GET /api/projects/{id}` | `proto:project:read` | 项目详情（不含原型明细，只含 `prototypeCount`/`publishedCount` 摘要） |
| 4.1.5 | `PUT /api/projects/{id}` | `proto:project:update` | 改 `name`/`description`；**`code` 传了也不生效**（返回 `PROTO_CODE_IMMUTABLE` 警告） |
| 4.1.6 | `DELETE /api/projects/{id}` | `proto:project:delete` | 软删除项目，级联其下全部原型；产物目录 7 天后 GC |
| 4.1.7 | `POST /api/projects/{id}/archive` | `proto:project:archive` | 归档：其下所有原型链接立即返回"已下架"页 |
| 4.1.8 | `POST /api/projects/{id}/unarchive` | `proto:project:archive` | 恢复上架 |
| 4.1.9 | `GET /api/projects/{id}/members` | `proto:project:read` | 成员列表。**一期必须有**：`publisher`/`viewer` 的 `data_scope=member` 依赖成员数据，没有它这两个角色登录后项目列表恒为空 |
| 4.1.10 | `PUT /api/projects/{id}/members` | `proto:project:update` | 覆盖式设置成员（写 `member_role` 但一期不据此做差异授权）。创建项目时自动把创建人写成 `owner` |

> **4.1.10 的实现约束（M2 实施中定死）**：请求体是 `{ members: [{ userId, memberRole? }] }`，`memberRole` 省略时按 `viewer` 落。但**创建人（`created_by`）的 `owner` 不接受请求改写**——请求里带上创建人却不给 `memberRole` 时，服务端把这一条强制回 `owner`；请求里没带创建人时服务端自动补上。否则一次"只改名单不改角色"的覆盖式保存就会把项目变成没有 owner（`owner` 承载的是"谁建的"这一事实，与 P1 才做的差异授权无关）。响应回更新后的成员列表（`{ userId, username, realName, memberRole, createdAt }`）。

**项目列表 `data.items[]`**

```jsonc
{
  "id": "9", "name": "CRM系统", "code": "crm",
  "description": "客户关系管理相关原型",
  "status": "published",                       // 派生值：published | draft | archived
  "prototypeCount": 6,
  "publishedCount": 5,                         // 已发布的原型数
  "visitsLast7d": 320,                         // 该项目下所有原型的近 7 天入口访问合计
  "createdByName": "张三",
  "updatedAt": "2026-10-06T14:30:00+08:00",
  "lastPublishedAt": "2026-10-06T14:30:00+08:00"
}
```
- `status` 是**派生值**（按决策 D-22 由原型聚合算出，不落库）：`archived`（`archived_at` 非空）/ `published`（存在已发布原型）/ `draft`（其余）
- 项目行**没有 `accessUrl`**——一个项目下有多条链接，给单条地址会产生误导。访问地址出现在原型列表里
- `visitsLast7d` 是聚合值，走 `proto_access_log → proto_prototype → project` 两级 join；项目列表页默认不排序它，只在需要时按它排（这个排序比其它排序慢，`sortBy=visits` 时前端显示 loading 稍长是可接受的）

**项目详情 `data`**：在列表字段基础上加 `archivedAt`、`createdAt`、`memberCount`、`prototypeCount` 明细（如 `{ total: 6, draft: 1, published: 5, archived: 0 }`）。

> **`createdAt` 的补充（M2 实施，见迭代实施计划 §9.2 DEV-9）**：本节原本只列了 `archivedAt`/`memberCount`/`prototypeCount`，而列表 `data.items[]` 只有 `updatedAt`。前端设计 §3.3「基本信息」要求项目详情显示**创建时间**，列表里没有这个字段、详情也没有，所以详情形态补 `createdAt`（ISO 串）。列表行**不加**——§3.2 的列定义里没有创建时间，加了就是没人消费的字段。落点在 `packages/shared` 的 `ProjectDetail`、`project.repo` 的 `ProjectRow`/`toRow` 与 `project.service` 的 `buildDetail` 三处，契约改动只走 shared（§3.7 红线：框架 `packages/**` 不动，我们的 `packages/shared` 是契约唯一来源）。

### 4.2 项目编码校验

```jsonc
// GET /api/projects/check-code?code=crm
{ "available": false, "reason": "CODE_TAKEN",
  "message": "该编码已被项目「CRM系统」占用",
  "suggestion": "crm-2" }
```
规则：格式 `^[a-z0-9]+(-[a-z0-9]+)*$`，长度 1~63；不得为保留字（`api`、`admin`、`static`、`assets`、`p`、`login`、`health`、`system`、`proto`、`www`，常量在 `packages/shared/src/constants/reserved-codes.ts`）；不得与在用项目重复。**`code` 为空是合法的**，返回 `{ available: true, generated: "p-7f3k9m2x" }` 告诉前端"留空将生成这个"。前端在输入框失焦时调用，把 `reason` 映射成字段下的小字提示。

### 4.4 访问策略（原型级）

- 请求：

```jsonc
{
  "accessMode": "password",       // public | password | member
  "password": "newpass123"       // accessMode=password 且需要改密码时传；不传表示沿用旧密码
}
```

> **原设计**：本节请求体还有一个 `"memberIds": ["3", "7"]`（`accessMode=member` 时的可访问成员，覆盖式；P1 细化到成员角色）。
> **修订说明（M2 实施，见迭代实施计划 §9.2 DEV-9）**：`memberIds` 已从请求契约移除。理由：权限模型 §6.2 规定"原型不单独判数据权限，一律通过父项目判定"，那么 member 档的可访问人**只能**是父项目成员——原型级再存一份成员名单就是两套口径，且 `proto_prototype` 本就没有承载它的表结构。现在 `memberIds` 只出现在**响应**的 `detail` 里（由 `proto_project_member` 派生的只读值），请求侧带它会被 `.strict()` 校验判为未知键（400）。可访问成员的增删一律走 §4.1.10 `PUT /api/projects/{id}/members`。
- 响应：`data` 为更新后的原型详情
- 副作用：`policy_version + 1`（**该原型**的旧解锁 Cookie 立即失效）、写 `sys_oper_log`（不写 `proto_release_event`——策略变更不是版本事件）
- 校验：`accessMode=password` 且既无 `password` 又无既有 `password_hash` → 400 `PROTO_POLICY_PASSWORD_REQUIRED`；密码强度 ≥6 位
- **策略是原型级而非项目级**（决策 D-21）：同一项目下"给客户看的登录页"与"只给内部看的流程页"可以设成不同策略，互不影响

## 5. 发布与版本

### 5.1 POST `/api/releases` —— 上传并发布（核心接口）

一个接口覆盖三种场景（对应"上传 HTML 原型"抽屉的两种模式与"上传发布"页），**不拆成多个接口**：

| 场景 | 请求中携带 |
| --- | --- |
| 新建项目 + 新建原型 + 发布 | `project` JSON（name/code/description）+ `prototype` JSON（name/code/description）+ `file` |
| 已有项目 + 新建原型 + 发布 | `projectId` + `prototype` JSON + `file` |
| 已有原型 + 发新版本 | `prototypeId` + `file`（可选 `note`） |

- 权限：`proto:prototype:publish`；需要新建项目时额外要求 `proto:project:create`，需要新建原型时额外要求 `proto:prototype:create`
- 请求：`Content-Type: multipart/form-data`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `file` | File | ✓ | zip 文件，≤100MB（`MAX_UPLOAD_BYTES` 可配） |
| `prototypeId` | string | 三选一 | 已有原型 ID（追加版本场景） |
| `projectId` + `prototype` | string + JSON | 三选一 | 已有项目下新建原型；`prototype` = `{ "name": "...", "code": "...", "description": "..." }`，`code` 留空自动生成 |
| `project` + `prototype` | JSON + JSON | 三选一 | 全新建；`project` = `{ "name": "...", "code": "...", "description": "..." }` |
| `note` | string | ✗ | 版本说明，≤300 字 |
| `force` | boolean | ✗ | 内容与该原型当前版本一致时是否强制发布（默认 `false`，此时返回 `UPLOAD_DUPLICATE_CONTENT` 提示） |
| `headers.Idempotency-Key` | string | ✗ | 幂等键 |

- 响应：**HTTP 202**

```jsonc
{ "code": 0, "data": { "taskId": "128", "projectId": "9", "prototypeId": "31", "accessPath": "/p/crm/crm-p01" }, "error": null, "message": "ok" }
```
- 行为：流式落临时文件 → **同步轻校验**（大小、zip 魔数、条目数上限、路径合法性初查）→ 不合格立即返回 4xx（此时 `data` 为空，错误码见 §8，**不落任何库记录**）→ 合格则**在一个事务里**落库 `project`（如需）/`prototype`（如需，`status='draft'`）/`proto_upload_task`，然后交给 Worker，立即返回 `taskId`
- 前端拿到 `taskId` 后轮询 §5.3

> **为什么在受理阶段（而不是处理完成时）就落库原型**：① 编码唯一约束提前生效，两个并发任务抢同一编码时第二个立刻失败，而不是跑完全部解压才冲突；② 发布失败时保留一个 `draft` 原型，用户可以点「重试」直接复用，不必重填表单；③ 原型详情页能看到"正在发布中"的任务。代价是失败会留下草稿原型——草稿本来就允许存在，列表里可见可删。

### 5.2 为什么不把解压放在这个请求里

100MB 的包解压 + 路径改写耗时不可控（几秒到几十秒），放在请求里会撞上 axios 默认 10 秒超时与网关超时，还会让"上传进度"和"处理进度"混在一起无法展示。拆成"上传 → 任务 → 轮询"后，前端能明确区分两段进度（见前端设计 §9）。

### 5.3 GET `/api/upload-tasks/{id}` —— 任务状态（轮询）

- 权限：`proto:prototype:publish`，且任务所属原型在数据范围内
- 响应 `data`：

```jsonc
{
  "taskId": "128", "projectId": "9", "prototypeId": "31",
  "status": "processing",                       // pending|processing|success|failed|canceled
  "progress": 65, "stage": "postprocess",        // validating|extracting|postprocess|committing
  "sourceName": "login-prototype.zip", "sourceSize": 3145728,
  "release": null,                               // status=success 时给出
  "warnings": [ { "code": "REWRITE_ABSOLUTE_PATH", "count": 12,
                  "message": "已将 12 处根绝对路径改写为 /p/crm/crm-p01/ 前缀" } ],
  "error": null                                  // status=failed 时给出，见 §8
}
```
- 轮询节奏：前端 1s 一次，最多 120 次（2 分钟）；超过后停止并提示"处理时间较长，请稍后在原型详情查看结果"
- 成功时 `release` 字段：

```jsonc
{ "id": "77", "versionNo": 3, "entryFile": "index.html", "fileCount": 42,
  "totalBytes": 3145728, "contentHash": "a1b2...",
  "projectId": "9", "prototypeId": "31",
  "accessPath": "/p/crm/crm-p01", "accessUrl": "https://proto.company.com/p/crm/crm-p01",
  "publishedAt": "2026-10-06T14:30:00+08:00" }
```

### 5.4 GET `/api/prototypes/{id}/releases` —— 版本列表

- 权限：`proto:release:list`
- 分页；`data.items[]`：

```jsonc
{ "id": "77", "versionNo": 3, "status": "ready", "isCurrent": true,
  "entryFile": "index.html", "fileCount": 42, "totalBytes": 3145728,
  "sourceName": "login-prototype.zip", "sourceSize": 3145728,
  "note": "首页改版", "createdByName": "张三", "createdAt": "...",
  "warnings": { "htmlRewrites": 12, "cssRewrites": 3 } }
```
- `versionNo` 是**原型内**的序号：`crm-p01` 的 v3 与 `crm-p02` 的 v3 是两个独立序列

> **修订说明（M3-T14 实施，偏差 DEV-24）**：上面这一版只有 `warnings` 计数，没有 place 承载前端设计 §3.5 要求的"点某条展开该版本的发布报告"（报告是逐条告警项 + 人话文案，不是一个数字能表达的）。实现给版本行**加一个字段**：
>
> ```jsonc
> "report": [
>   { "code": "REWRITE_ABSOLUTE_PATH", "count": 2,
>     "message": "已将 2 处根绝对路径改写为 /p/crm/crm-p01/ 前缀（HTML 0 处，CSS 2 处）" },
>   { "code": "BASE_TAG_FOUND",
>     "message": "文件 \"index.html\" 含 <base href>，可能影响路径解析 — 建议移除 base 后重新导出" }
> ]
> ```
>
> 取数来源是 `proto_release.manifest.warnings`（机制 §2.7 落库时就带着），**不是 §5.3 任务行的副本**——任务行按 §4.3 只保留 90 天会被 GC 回收，而发布报告是版本自身的长期属性（"为什么这一版打开和本地不一样"要一直能回答）。`warnings.{htmlRewrites,cssRewrites}` 原样保留：它是 §3.5 时间线上"这一版改写过路径"的角标数据，来自 `manifest.rewrites`，与 `report` 一个是数、一个是话，不重复判定。文案由服务端生成、界面原样显示（机制 §8.2），前端不再算第二遍。实测读数（`GET /api/prototypes/10/releases`，v9）：`report` 两条，`count=2` 与 `warnings` 的 `{html:0, css:2}` 同批产物。

### 5.5 POST `/api/prototypes/{id}/rollback` —— 回滚

- 权限：`proto:prototype:rollback`
- 请求：`{ "releaseId": "70", "reason": "新版样式被否" }`
- 响应：`data` 为更新后的原型详情
- 副作用：`prototype.current_release_id = releaseId`（事务内完成）、`published_at = now()`、写 `proto_release_event(rollback, from=旧, to=新)`、写 `sys_oper_log`
- 校验：目标版本属于该原型且 `status='ready'`（不能回滚到已标记 broken/deleted 的版本）；原型已归档 → 先恢复上架，否则 400 `PROTO_ARCHIVED`；**原型所属项目已归档** → 同样 400 `PROJECT_ARCHIVED`
- **只影响这一个原型的链接**：同项目下其它原型不受影响（这是三级模型的核心收益）

### 5.6 DELETE `/api/prototypes/{id}/releases/{releaseId}`

- 权限：`proto:release:delete`
- 行为：不允许删除**当前生效版本**（400 `RELEASE_IS_CURRENT`）；其余置 `status='deleted'` + `deleted_at`，产物延迟 7 天物理删除；写 `proto_release_event(delete_version)`

### 5.7 GET `/api/prototypes/{id}/releases/{releaseId}/download`（P1）

- 权限：`proto:release:download`
- 行为：把该版本产物重新打成 zip 流式返回（`archiver`），文件名 `{原型编码}-v{versionNo}.zip`。用于"把上线的那版打包给开发"

### 5.8 GET `/api/prototypes/{id}/events` —— 版本时间线

- 权限：`proto:release:list`
- 分页，`data.items[]`：

```jsonc
{ "id": "41", "eventType": "rollback", "fromVersionNo": 3, "toVersionNo": 1,
  "operatorName": "张三", "reason": "新版样式被否", "createdAt": "..." }
```
- 事件类型：`publish`（发布新版本）、`rollback`、`republish`（内容未变时的强制重发）、`unpublish`（下架）、`delete_version`
- 项目级动态（项目详情页用）走 `GET /api/projects/{id}/events`，是同一张表按 `prototype.project_id` 聚合后的视图，字段多一个 `prototypeName` 与 `prototypeCode`

### 5.9 GET `/api/releases/link-preview` —— 发布前的访问链接预览（M3 新增，原设计无此接口）

> **这一节是 M3-T11/T13 实施时新增的（偏差 DEV-25）**：§5 原来只到 §5.8，"发布后链接是什么样"没有接口可问。设计里三处要显示完整访问链接（新建项目+原型的抽屉、新建原型的抽屉、上传发布页选中原型后的摘要行），而 URL 的拼装权在服务端（§4.3 的 `accessUrl` 口径 + §1.5"不要在多个前端页面里各写一遍域名拼接"）——前端自己拼就等于把 `PUBLIC_BASE_URL` 复制到三个组件里，换域名时漏一处就是一个错链接。所以给一条只读预览接口，URL 只服务端算一次。

- 权限：`proto:prototype:publish`（预览的用途就是发布前，用同一枚码，不新增"没人会单独勾选"的码）
- query：`projectCode`、`prototypeCode`（两段都必须已确定：手填值，或 `check-code` 返回的 `generated`）
- 响应 `data`：`{ "accessPath": "/p/p-z2jo4sob/p-z2jo4sob-p02", "accessUrl": "http://127.0.0.1:3100/p/p-z2jo4sob/p-z2jo4sob-p02" }`
- **不查库、不判存在性**：它对"将要生成的链接"负责，与 `check-code` 各管一段（后者判重名与建议，前者判最终 URL）。因此手填一个还没创建的编码照样返回 200，这是预览该有的行为
- 校验：编码格式不合法 → `400 PROTO_CODE_INVALID`，话术与新建项目/新建原型同源（复用 `assertProjectCodeFormat`/`assertPrototypeCodeFormat`，预览和提交不会报出两种不同的编码错误）；缺任一段 → `400 PARAM_INVALID`
- 实测：`?projectCode=p-z2jo4sob&prototypeCode=p-z2jo4sob-p02` → `{"accessPath":"/p/p-z2jo4sob/p-z2jo4sob-p02","accessUrl":"http://127.0.0.1:3100/p/p-z2jo4sob/p-z2jo4sob-p02"}`；`projectCode=中文` → 400 并点名格式规则；只给 `projectCode` → `400 参数不合法：prototypeCode：Required`

## 6. 访问记录

### 6.1 GET `/api/access-logs`

- 权限：`proto:accesslog:list`
- query：`page`、`pageSize`、`projectId`（筛该项目下所有原型）、`prototypeId`（筛单个原型）、`startTime`、`endTime`、`result`（`ok`/`denied_401`/`denied_403`/`not_found`）、`keyword`（IP/UA 模糊）
- 分页；`data.items[]`：

```jsonc
{ "id": "9021", "projectId": "9", "projectName": "CRM系统",
  "prototypeId": "31", "prototypeName": "登录页演示", "prototypeCode": "crm-p01",
  "routeKey": "crm/crm-p01", "versionNo": 3, "path": "/p/crm/crm-p01/", "result": "ok",
  "userId": null, "visitorName": null,          // member 档已登录时才有
  "ip": "116.226.1.x", "browser": "Chrome 141", "os": "macOS",
  "device": "desktop", "referer": "https://chat.company.com/...", "isBot": false,
  "createdAt": "2026-10-06T14:30:00+08:00" }
```
- `prototypeId` / `prototypeName` / `prototypeCode` **在编码不存在或已被删除时为 `null`**，此时靠 `routeKey`（形如 `crm/crm-p01`）说明访问的是什么路径。列表页对这类行显示为「无效链接」而不是空白
- 说明：IP 默认**脱敏展示**（最后一段打码），`system:log:list` 及以上权限可请求 `maskIp=false` 看全量

> **原设计 + 修订说明（M4-T10，计划 §9.2 DEV-34）**——本节原来只给了权限、query 清单和一个响应样例，实现时以下六处需要补口径（都不改对外字段集合）：
>
> 1. **数据范围（原设计完全没写）**：publisher/viewer 都握着 `proto:accesslog:list`，而 `data_scope=member`（权限模型 §3.5），行里却带着访客 IP、UA、来源与登录用户名——不叠范围就等于让任一 viewer 读到别人项目的流量。判定沿用项目列表那一份 `projectScopeWhere`，在这里解析成**两个集合**：可见项目下的原型 `id` ∪ 可见项目的 `code`。要两个是因为 `prototype_id` 为空的行（编码不存在那一路）只能靠 `route_key` 第一段归属，而"原型的可见性一律由父项目决定"（权限模型 §6.2）意味着这一行属于谁的项目就必须对谁可见。两个集合都**不叠 `deletedAt: null`**：成员该看得见"旧链接还在被访问"，而那些行恰恰挂在已软删的原型/项目上——行内的名字类字段仍按上面的样例降级为 `null`。`projectId` 筛选与范围**求交而不是替换范围**；范围或筛选解析不出可见对象时回**空页 + `total:0`，不是 403**（筛一个不存在或看不见的项目，正确答案就是"没有记录"；403 会把"我筛错了"说成"你没权限"）。
> 2. **`maskIp=false` 的失败方式**：缺那枚码时**忽略参数继续打码**，不报 403——§的措辞是"可请求"，即这是请求者的附加权限而不是本接口的前置条件。资格按**权限码**判定（`system:log:list`）而不是按角色名，超管短路；默认路径（不传或传 true）**一次权限查询都不发**。
> 3. **打码口径以规范句为准，不以样例为准**：实现是"只削最后一段"→ `116.226.1.x`；**原样例写的是 `116.226.x.x`**（一次削两段），已按实现改正。一次削两段就没法再按 /24 看出"同一个网段来的人"，而这列存在的理由恰恰是这个（以及 UV 为什么要带 ip）。扩展：IPv6 把最后一组换成 `xxxx`，`::ffff:116.226.1.2` 这类映射地址同样只留前缀（结果是 `::ffff:xxxx`）；形状认不出却含 `.`/`:` 的值（`1.2.3.4:8080`、`10.0.0.0/8`）**只留第一段**、其余整段换 `x`——判不出哪段是"最后一段"时宁可少给；既不含 `.` 也不含 `:` 的根本不是 IP（主机名），原样返回。
> 4. **排序**：`created_at desc, id desc`。异步缓冲是 500 条一批提交的，同一毫秒落多条日志，没有 `id` 当第二把尺子就会在翻页时重复或漏行。
> 5. **参数校验的四条 400**：`result` 越界、`startTime > endTime`、重复键（`?result=ok&result=not_found` 在 Fastify 解析后是数组）、`keyword` 缺失/超 120 字符。前两条刻意不"宽容"：把越界的 `result` 当"没筛"会返回全量，用户看到的是"筛选没生效"而不是"值不对"；静默交换区间等于替用户改了一次查询条件，他会在错误的窗口里得出"最近没人访问"的结论。`keyword` 对 `\ % _` 做 LIKE 转义（不转义时搜 `10.` 会命中全表），`ip` 是 `inet` 所以显式 `::text` 再 `ilike`。
> 6. **读到字典外的值怎么办**：`result` 不在四档内按 `not_found` 显示、`device` 越界给 `null`（界面显示"-"）。这一列是 varchar + 迁移里的 CHECK，脏值只可能是人为改库或将来加档没同步前端；为此让整页 500 或编一个档位都不如降级显示。**原样例写的是 `"os": "macOS 15"`**，已按实现改正为不带版本的 `macOS`（Mac 的 UA 里没有系统版本段，`Windows NT 10.0` 那种写法才有；见 [原型发布与访问机制.md](./原型发布与访问机制.md) §6.1）。
>
> 另有一处不影响判定的写法差异记录在此以免被当成不一致：样例的 `createdAt` 写 `+08:00`，实现统一回 UTC 的 `Z` 形式（`toISOString()`，与全仓其它读接口同一个口径）。两者是同一时刻的两种写法，前端按本地时区渲染。

### 6.2 GET `/api/access-logs/summary`

- 权限：`proto:accesslog:list`
- query：`projectId` 或 `prototypeId`（都可选，都空表示全局）、`days`（默认 7，上限 90）
- 响应 `data`：

```jsonc
{
  "pv": 903, "uv": 118, "denied": 26, "botPv": 41, "invalidPv": 7,
  "daily": [ { "date": "2026-10-06", "pv": 152, "uv": 31 } ],
  "topPrototypes": [ { "prototypeId": "31", "name": "登录页演示", "code": "crm-p01",
                       "projectName": "CRM系统", "pv": 320 } ],
  "topReferers": [ { "referer": "https://chat.company.com", "pv": 210 } ]
}
```
- `invalidPv` 是访问了不存在/已删除编码的次数，单独统计：这个数字异常升高通常意味着**有人拿旧链接在访问**（说明切版本/删原型的影响面），值得看见。计数条件是 `result='not_found'` **且这一行的原型连不上或已软删**（`prototype_id` 为空，或 `proto_prototype.deleted_at` 非空）——机制 §6 有两类记录都写 `not_found`：一类是"编码不存在/原型已删除"（本指标的数据源），另一类是"原型活得好好的、发布产物里少了一个文件"（白屏线索，不该冒充"旧链接还有人用"）。只按 `result` 数就会把后一类算进来，同一屏上这张卡片与明细表里显示为「无效链接」的行数就各说一套（计划 §9.2 DEV-35）
- 榜单是**按原型**而不是按项目：三级模型下"哪个原型被看得最多"才是有用的信息
- UV 口径：`date + ip + ua` 去重（与未决问题 Q-2 的一致口径）

> **原设计 + 修订说明（M4-T10，计划 §9.2 DEV-34）**——本节给了五个指标名、`days` 的默认与上限、两份榜单样例，实现时以下七处需要补口径（对外字段名与含义不变）：
>
> 1. **`days` 的三种失败分得很开**：缺失给 7；**数字**越界（`days=0`、`days=999`）夹到 `1..90` 而不是报错——图表少一天不值得让整页 400，而下限 1 是"只想要今天"的合理请求；**非数字**（`days=abc`）在 schema 层就 400。夹取与报错不能混成一种失败，否则"我填错了"和"我填得太大"在界面上长一样。
> 2. **窗口是"最近 N 个本地日历日（含今天）"，且只有下界**。不用 `now - days*24h` 的滚动窗口：§6.2 的产物是按天折线，滚动窗口会让第一天只统计到半天数据，图上看着像流量腰斩（项目详情里那个 `visitsLast7d` 用滚动窗口是因为它不是按天图）。上界不写 `<= now()`，否则时钟差会把刚落库的行切掉。日期用 `new Date(y, m, d - n)` 递增而不是加 86400000 毫秒——跨夏令时/时区调整那天真的不是 24 小时。
> 3. **`daily` 补齐零值日**：库里没记录的日子也要在数组里出现（`pv: 0`），否则折线把中间那几天直接连起来，看着像"那几天流量正常"。空结果（无可见范围）同样返回补齐后的 `daily` 而不是空数组——图是常驻卡片，空数组会让整块不渲染。
> 4. **分桶与本地化分工**：SQL 里 `date_trunc('day', created_at)` 回的是 `date` 值，**格式成本地日历日标签这件事只在服务层做一处**。数据库会话时区与进程时区不是同一个保证，在 SQL 里就格式化成字符串会出现窗口（本地算）与桶（库算）错一天，表现为"今天的数据挂到昨天"。
> 5. **两个榜单的集合比明细窄**：`topPrototypes` 与 `topReferers` 只在 `result='ok'` 的行上算（被拒和无效链接进"哪个原型被看得最多"没有解释力），且 `prototype_id is not null`；`topReferers` 按 referer 的 **origin**（`scheme://host[:port]`，正则取出，query 与 path 进不了分组）聚合，origin 解析不出的行不进榜。榜单长度 10 是**文档外的常量**（样例没给条数），不为它开入参。
> 6. **`prototype_id` 没有外键**（数据库设计 §4.1.16），所以榜上的 id 可能指向已经没了的行。取不到名字的**从榜里丢掉**，而不是显示"未知原型"——那条记录已经被 `invalidPv` 计过，出现在"最热门"里只会让人以为数据坏了。
> 7. **五个指标与明细严格同口径**：汇总、趋势、两张榜共用同一份条件组装（含 §6.1 第 1 条的数据范围），拆成两处判定就会出现"卡片数字与折线/表格对不上"。`denied` 是 `denied_401` 与 `denied_403` 合并成一个数（界面只有一张卡片），`botPv` 是 `pv` 的子集（同为 `result='ok'`），`uv` 排除 bot（机制 §6：爬虫不进 UV）。聚合查询恒应有一行，真没有就抛错而不是猜五个 0——否则界面会显示"一个全 0 的正常平台"。

## 9. 内部接口（供 nginx `auth_request` 调用，不对公网开放）

### 9.1 GET `/api/access/check` —— 访问决策

- 调用方：nginx 内部子请求（`proxy_pass` 到 `127.0.0.1:3100`）
- 鉴权：**拒绝公网来源**——Node 侧校验 `X-Real-IP` 属于本机/内网白名单（`ACCESS_CHECK_ALLOW_CIDRS`），非白名单直接 403。**该接口不接受任何凭据参数**（路径/查询串里的 token 一律不认），防止被当成"权限探测 API"滥用
- 请求头（nginx 传入）：

| 头 | 内容 | 说明 |
| --- | --- | --- |
| `X-Original-URI` | 原始请求 URI，如 `/p/crm/crm-p01/index.html?x=1` | nginx 用 `$request_uri` 填入，因为 `proxy_pass` 的固定路径无法携带它。服务端从这条 URI 里解析出**两段编码** |
| `Cookie` | 原始 Cookie（`$http_cookie`） | **身份的唯一来源**：密码档读 `proto_access_p{原型ID}`，member 档读 `proto_sess` |
| `X-Real-IP` | `$remote_addr` | 用于来源校验、解锁限速与放行日志 |

> **不读 `Authorization` 头**：浏览器发起顶层导航与静态资源请求时不会带该头，用它判定 member 档必然全部被拦（设计修正详见 [原型发布与访问机制.md](./原型发布与访问机制.md) §5.4）。签名 Cookie 与 `token_version` 校验的组合既能识别身份，也能让"改密码/被禁用"立即生效。

- 响应：**必须按下面的状态码与响应头返回，nginx 依赖它们**

| 状态码 / 头 | 取值 | nginx 用途 |
| --- | --- | --- |
| `200` | — | 放行，返回静态文件 |
| `401` | — | `error_page 401` → 密码门面页（仅当该原型是密码档） |
| `403` | — | `error_page 403` → 提示类门面页（需登录 / 无权限 / 已下架） |
| `404` | — | `error_page 404` → 链接失效门面页（编码不存在 / 未发布 / 只有一段路径） |
| `X-Proto-Release-Dir` | `releases/9/31/77` | **200 时必带**；nginx 用**白名单 map** 取到后作为变量 `root`，决定服务哪个版本目录（为什么不能直接取见部署方案 §5.1 第 4 条） |
| `X-Proto-Reason` | `NEED_PASSWORD` / `NEED_LOGIN` / `NO_PERMISSION` / `PROTOTYPE_ARCHIVED` / `PROJECT_ARCHIVED` / `NOT_FOUND` / `NOT_PUBLISHED` | nginx 透传给门面页，用于选择展示哪种形态 |
| `X-Trace-Id` | — | 透传给门面页，便于报障时对照日志 |

- 响应体对 nginx 无意义（但为调试方便，仍返回统一包装结构，`data` 里带 `reason`）
- 被拒时的错误码口径：`errorCode` **就等于原因码本身**（不再另造一套 `ACCESS_*` 名字），`error`/`message` 固定为「访问未通过」，不回显项目名/原型名。实测样例：`404` + `X-Proto-Reason: NOT_FOUND` + `{"code":-1,"errorCode":"NOT_FOUND","error":"访问未通过"}`

> **原设计 + 修订说明（M4-T3，DEV-28）**：上面那行把 `X-Proto-Reason` 定成封闭的七个值，但同一节又要求「拒绝公网来源 → 403」，而 Gate M4-T3 的 C2 写"401/403/404 时带 `X-Proto-Reason`"——两者相撞：来源不合法时没有可用的原因值。实现取**第八个值 `SOURCE_NOT_ALLOWED`**，它**不进** `packages/shared` 的 `ACCESS_REASONS`（那个联合仍是七个，门面页与访问日志照原样消费），只在 `access.controller.ts` 一处出现。理由：那七个值的用途是让门面页选展示形态，而来源不合法根本不会走到门面页（正常部署下只有 nginx 用 `$remote_addr` 打这个口）；混进枚举会逼门面页处理一个它永远见不到的形态，还会让"访客没登录"与"有人在探测这个接口"在日志里混成一条。nginx 侧无需改动——它对 `error_page` 的透传是按查询串转发，不校验取值。这条的 `errorCode` 例外地用 `ACCESS_SOURCE_FORBIDDEN`（探测是本接口唯一的非决策分支）。

- 副作用：把决策结果写入 `proto_access_log`（异步队列，不阻塞响应；写失败只落本地日志）
- **性能**：该接口在原型每个子资源请求上都会被调用一次。对策：nginx 侧对 `auth_request` 结果**不做缓存**（保证权限即时生效），因此该接口必须极轻——一次 `proto_prototype` 按 `(project_id, code)` 的唯一索引查询（项目、原型在一条查询里 join 出来）+ 验签 Cookie，**禁止在此做联表统计**。

### 9.2 POST `/api/access/{projectCode}/{prototypeCode}/unlock` —— 密码档解锁

- 调用方：密码页表单（公网可达）
- 请求：`{ "password": "..." }`，`Content-Type: application/json`；只认 body 里的这一个字段，**不接受任何凭据参数**（query 里带 `token`、header 里带 `authorization` 一律无视）
- 请求体形状：`{password}` 必填、去首尾空白后 **1–72 字符**（与 argon2 的输入上限对齐），多余字段拒绝；不合法 → **400 `PARAM_INVALID`**（人话「请输入访问密码（最长 72 个字符）」），且**不进限速、不查库**
- 成功：`data: null` + `Set-Cookie: proto_access_p{原型ID}=<HMAC 签名>; Path=/p/{projectCode}/{prototypeCode}; Max-Age=86400; HttpOnly; SameSite=Lax`（`Secure` 由 `NODE_ENV` 派生：非 production 不下发，本地 http 才能用）
- 失败：403 `ACCESS_BAD_PASSWORD`（人话「访问密码不对，请再试一次」）；同 IP 对**同一条链接**连续失败 5 次锁定 10 分钟（429 `RATE_LIMITED`，人话「失败次数过多，请 10 分钟后再试」）
- 令牌格式与签名规则见 [原型发布与访问机制.md](./原型发布与访问机制.md) §5.2

> **原设计 + 修订说明（M4-T7/T8，DEV-32）**：原文只写了"密码对→发 Cookie、密码错→403、连错 5 次→429"三条，剩下四种到达本接口的情况没有规定；实现按**同一个 `decideAccess()` 口径**补齐，本接口不自己判断业务：
> ① **URL 两段编码不合法**（大写、超长、含穿越）→ 与 `/p/…` 直出与 `check` 一致的 **404 + `X-Proto-Reason: NOT_FOUND`**，而不是 400——否则"链接写错"与"链接不存在"在状态码上分叉，门面页要认两套；
> ② **该原型本来就不需要密码**（公开档 / 已解锁 / 已是 200）→ **200 `data: null` 且不设 Cookie**（`already-open`）：表单被重复提交或被书签重放时给一个无害的成功，而不是 400；
> ③ **决策给出的其它拒绝**（`NEED_LOGIN`/`NO_PERMISSION`/`*_ARCHIVED` → 403，`NOT_FOUND`/`NOT_PUBLISHED` → 404）→ 原样按 `check` 的拒绝体返回，带 `X-Proto-Reason`；
> ④ **限速的键**是"IP + 这条链接"（`{ip}|{项目编码}/{原型编码}`），不是字面的"同 IP"——按 IP 锁会把一个扫描器对某条链接的暴力尝试放大成**整个 IP 下所有原型都解不开**（办公网/NAT 后全是真人）；计数只在进程内存（与 `LoginLockService` 同口径），nginx 侧另有按 IP 的 `limit_req` 作第二层，重启丢计数可接受。
> 另外两处顺序约束：**限速先于任何查询**（锁住的请求不该能继续消耗数据库），**口令哈希只在这一条路径上读**（`password_hash` 不进 `check` 的热路径 select）。实测读数（dev 库 + `SERVE_STATIC=node`，真浏览器 + curl 双向）：正确密码 → `200` + `set-cookie: proto_access_p12=v1.3.1791413325.u1h_vhLJDItsHLilMZIfsCFQ2xcAk-HrDaqSRKa6JQU; Path=/p/p-z2jo4sob/p-z2jo4sob-p03; HttpOnly; SameSite=Lax; Max-Age=86400`（开发环境无 `Secure`）→ 页面 reload 后拿到原型本体，子资源 `css/app.css` 同 Cookie 下 `200 text/css`；错误密码 → 页面内联「访问密码不对，请再试一次」不跳转；连错 5 次后**用正确密码再提交仍是 429**（服务端与浏览器两侧同键同时观测到，锁的是键不是"这次猜对没猜对"）；公开档提交 → `200` 无 `set-cookie`；空 body、`{}`、`{"pass":…}`（字段名错）、空密码、纯空白、73 字符、多余字段、数组体 **8 种形状逐个 curl 实测都是 400 `PARAM_INVALID`**，紧接着同一条链接正确提交仍 `200`——证明形状拒绝发生在限速之前、不记进锁的计数。

> Cookie 名用**原型数字 ID**（`proto_access_p31`）而不是两段编码拼接：编码里允许 `-`，`{a}-{b}` 形式的拼接会有歧义（`a-b`+`c` 与 `a`+`b-c` 会撞成同一个名字）；数字 ID 全局唯一，无歧义，且不把编码写进 Cookie 名。

### 9.3 GET `/api/access/gate` —— 门面页

- 调用方：nginx `error_page` 代理（公网可达）
- query：`project`（项目编码）、`prototype`（原型编码，可能为空）、`code`（`401`/`403`/`404`）、`reason`、`from`（原始路径，用于登录后跳回）
- 鉴权：`@Public`，且**不套响应信封**（`@SkipEnvelope`）——这一条返回的是 HTML，不是 `{code,data,error}`
- 响应：`Content-Type: text/html; charset=utf-8` + `Cache-Control: no-store`，一个**自包含的极简 HTML 页面**（内联 CSS 与内联脚本，零外部文件；实测样式规则 16 条全部被浏览器解析，页内 `{` 计数 = `cssRules.length` = 16）：密码输入 / 去登录 / 无权限 / 已下架 / 链接无效五种形态，外加一个"暂时无法访问"兜底形态
- 说明：这个页面故意不走 SPA，因为它的受众可能是**外部客户**，不该看到管理台框架；且 nginx `error_page` 需要直接的 HTML 响应。`code=404` 时**不区分**"编码不存在"与"未发布"，避免被用来枚举原型（对应 R-9）
- 入参与取值收敛、各形态文案、`from` 的开放重定向防护，见 [原型发布与访问机制.md](./原型发布与访问机制.md) §5.3 的表与修订说明（M4-T6 / 计划 §9.2 DEV-30）。这里只强调接口层的三条：**任何不认的入参都往保守方向退，不因入参异常而报错**；**页面除访问者自己 URL 里的那两段编码外不含任何标识**（Gate G9：在源码里搜项目名/原型名，实测 0 命中）；**本接口恒 200**，对外的 401/403/404 由 nginx `error_page` 决定
- **副作用（M4-T9 / DEV-33，原设计未写）**：`code=404` 且 `from` 能解析成 `/p/{项目}/{原型}/…` 的**非入口**路径时，本接口会向访问记录缓冲送一条 `not_found`（并为此做一次 `(project_code, code)` 唯一索引查把 `prototype_id`/`release_id` 补上）。原因见机制 §6 的"记录点的分布"——"资源缺失"这一档在 nginx 形态下只有这里观察得到。**`from` 只用于补记这一条记录，绝不用于跳转或拼进页面**（跳转面见上一条的开放重定向防护）；`code=401/403` 与入口 404 由 `/api/access/check` 记，本接口不重复记；其余传入（含 `from` 不可解析、缺失、是入口路径）零副作用。这一条也意味着**人肉打开 `?code=404&from=…` 看形态会写进统计**（Gate G9 的查看源码动作实测会多出一行 `not_found`，属预期）
- 另一处与直觉不同的地方：这一条记录**没有 `user_id`**（界面显示"匿名"）。Cookie 本身是透传的（`proxy-common.conf` 只设 `Host`/`X-Real-IP`/`XFF`/`X-Forwarded-Proto`/`Connection`，不清 `Cookie`），所以这不是拿不到，而是**刻意不解析**：认出登录者要走 `resolveSession()`（验签 + 查用户表 + 比项目数据范围）三次查询，而这一行的价值在"哪个文件缺失"，不在"谁看见了空白页"。有身份的那一侧仍然齐全——入口被拒与入口成功两类行都由 `/api/access/check` 记，那里本来就要算 `sessionUserId`
