# ProtoHub 平台设计方案

> 状态：设计待评审 ｜ 日期：2026-10-06 ｜ 关联：本文档为总纲，细节见同目录各专题文档

---

## 1. 背景与问题

当前流程：产品经理用设计工具导出 HTML（或打包 zip）→ 通过聊天工具发给开发 → 开发或运维把文件丢到服务器 nginx 目录、手工加一段 location 配置。带来的问题：

| 编号 | 现状问题 | 具体表现 |
| --- | --- | --- |
| P-1 | 分发链路不可靠 | 群里翻"哪个是最新版"，出现 `原型-v3-final-最终版(1).zip` |
| P-2 | 上线依赖运维 | 每加一个原型都要改 nginx 配置、重启，环境强耦合 |
| P-3 | 链接不固定 | 每次换文件链接可能变，已发出去的链接失效 |
| P-4 | 无访问反馈 | 不知道客户/同事有没有打开过、什么时候打开过 |
| P-5 | 打开白屏率高 | 原型里写死 `/assets/...` 绝对路径，换个路径就加载失败，要开发排查 |
| P-6 | 无法控制可见范围 | 保密项目只要链接被转发就等于公开 |
| P-7 | 无版本概念 | 改坏了只能重新问产品经理要文件 |

## 2. 目标与成功标准

**一句话目标**：产品经理把 zip 拖进去，30 秒内拿到一个稳定的、可控制访问范围的链接，并能随时回滚和看到访问情况，全程不需要开发或运维介入。

**可验收的成功标准**

| 指标 | 目标值 | 验收方式 |
| --- | --- | --- |
| 自助发布耗时 | ≤20MB 原型从点"立即发布"到链接可访问 ≤10s（P95）；100MB ≤60s（P95） | 用 3 个真实原型包实测记录 |
| 原型访问性能 | nginx 直出，缓存命中时 TTFB ≤100ms | `curl -w '%{time_starttransfer}'` × 50 次取 P95 |
| 变更即时生效 | 改密码 / 下架 / 切版本后，已打开页面的用户刷新即生效 ≤1s | 浏览器实测（见发布机制文档 §7 缓存取舍） |
| 平台自身鉴权 | 无权限接口返回 403、无登录返回 401，前端菜单与按钮随权限变化 | 用 4 个内置角色账号逐项点测 |
| 权限变更生效 | 改角色权限后，操作者下次操作即被拦截（无需重新登录） | 后端每次请求查库校验，不缓存权限码 |

**明确不做（本期）**

- 原型的在线可视化编辑（HTML/DOM 编辑器）
- 原型与代码仓库 / CI 的自动联动
- 多租户（一个部署服务多个互不可见的组织）
- 灰度分流、A/B 测试

## 3. 范围与分期

### P0（一期，必须）

登录鉴权、用户/角色/权限/菜单管理（用户明确要求）、项目 CRUD、上传发布（zip）、版本列表与回滚、三档访问控制、访问记录、工作台。

### P1（二期）

项目成员授权（细粒度）、访问记录导出 Excel、分享二维码、原型内批注（在原型上画圈写意见）、发布成功通知（邮件/企微）、上传分片续传。

### P2（三期）

原型内评论与回复、对象存储（S3/MinIO）正式启用、自定义域名（客户用自己的域名看原型）、SSO/LDAP 对接、原型访问趋势看板。

## 4. 名词表（统一语言）

**三级模型：项目 → 原型 → 版本。** 一个项目下可以有很多个原型，每个原型是**一条可独立分享的访问链接**，每个原型有自己的版本历史。

```
项目 Project「CRM系统」            code = crm          （容器，管归档与成员范围）
├── 原型 Prototype「登录页」        code = crm-p01      → /p/crm/crm-p01
│   └── 版本 Release  v1 v2 v3 …  （不可变快照，其中之一为当前生效版本）
├── 原型 Prototype「订单流程」      code = crm-p02      → /p/crm/crm-p02
└── 原型 Prototype「客户详情」      code = crm-p03      → /p/crm/crm-p03
```

| 术语 | 标识 | 定义 | 注意 |
| --- | --- | --- | --- |
| 平台 | ProtoHub | 本系统 | |
| 项目 | `Project` | 原型的容器，对应"原型项目"列表里的一行 | 与"项目组/团队"无关，本期无团队实体（见 §12 Q-1） |
| 项目编码 | `project.code` | 项目唯一短标识，访问路径的第一段 | 可自定义；留空随机生成；**创建后不可修改**（D-14） |
| 原型 | `Prototype` | **一条可独立分享的访问链接**及其版本历史的载体 | 这是分享与鉴权的最小单位 |
| 原型编码 | `prototype.code` | 原型短标识，访问路径的第二段，**项目内唯一** | 可自定义；留空按 `{项目编码}-p{序号}` 生成；不可修改 |
| 访问路径 | — | `https://proto.company.com/p/{项目编码}/{原型编码}` | 决策 D-19 |
| 发布版本 | `Release` | 一次上传产生的**不可变**产物快照 | 一个原型有 0..N 个版本，其中一个为当前生效版本 |
| 产物 | Artifact | zip 解压、后处理后的静态文件集合 | 存放在版本目录下 |
| 入口文件 | `entry_file` | 版本被访问时默认返回的 HTML | 通常 `index.html`，发布时自动探测 |
| 发布任务 | `UploadTask` | 一次上传的处理过程（异步） | 有 pending/processing/success/failed 状态 |
| 访问策略 | `access_mode` | `public` 公开 / `password` 密码 / `member` 仅平台成员 | **原型级**配置（同一项目下不同原型可给不同的人看，D-21） |
| 状态（原型） | `prototype.status` | `draft` / `published` / `archived`，落库 | |
| 状态（项目） | — | `已归档` / `已发布` / `草稿`，**由原型聚合派生**，不落库 | 派生规则见数据库设计 §4.2.1 |
| 权限码 | Permission Code | 形如 `proto:prototype:publish` 的操作标识 | 清单见权限模型设计文档 |
| 数据权限 | `data_scope` | 角色能看到的**项目**范围：`all` / `own` / `member` | 数据范围停在项目层，项目内所有原型随项目一起可见 |

## 5. 总体架构

```
                        ┌──────────────────────────────────────────────────┐
   分享链接              │  nginx  proto.company.com                        │
   /p/crm/crm-p01 ────▶  │                                                  │
                        │  location = /            → admin SPA (history)   │
                        │  location /assets/**     → admin SPA 静态资源     │
                        │  location /api/**        → 127.0.0.1:3100 (Node)  │
                        │  location /p/{项目}/{原型}/**                     │
                        │                          → auth_request 决策      │
                        │                             ↓ 2xx 放行           │
                        │                           alias 版本目录(直出)   │
                        │                             ↓ 401/403/404       │
                        │                           error_page → 门面页     │
                        └────────────┬──────────────────────┬──────────────┘
                                     │ /api/**              │ /__proto_auth (内部)
                        ┌────────────▼──────────────────────▼──────────────┐
                        │  Node 服务 (NestJS + Fastify, pm2)                │
                        │   auth │ system(user/role/menu) │ project        │
                        │   prototype │ release(发布流水线) │ access        │
                        │   accesslog(访问记录) │ dashboard                 │
                        └───────┬───────────────────────────┬──────────────┘
                                │                           │
                     ┌──────────▼─────────┐      ┌──────────▼───────────────┐
                     │ PostgreSQL 17      │      │ StorageAdapter            │
                     │ 业务元数据/权限/日志 │      │  v1: 本地磁盘              │
                     │ 不含静态产物本身    │      │  P2: S3/MinIO             │
                     └────────────────────┘      └──────────────────────────┘
```

**三个必须理解的设计要点**

1. **静态产物不进数据库**。数据库只存元数据与指针（各原型的当前版本 ID、内容哈希、文件清单摘要），产物文件由存储层管理、由 nginx 直出。数据库因此保持小而快。
2. **鉴权口径唯一在 Node**。nginx 只做"问一次"（`auth_request`），三档策略的全部判断逻辑在 Node 的 `/api/access/check`，开发模式（无 nginx，Node 直接返回静态文件）与生产模式复用同一个决策函数，不会出现两套规则。
3. **版本切换是改指针，不是搬文件**。`prototype.current_release_id` 指向哪个版本，该原型的链接就服务哪个版本，因此回滚是毫秒级 DB 操作，且**互不影响**：更新 crm-p01 不会影响 crm-p02 的链接。

| Vue | vue | 3.5.41 | |

| 语言 | typescript | ^6.0.3 | |
| UI 库 | ant-design-vue | ^4.2.6 | |
| 样式 | tailwindcss | ^4.3.3 | 与 vben 内置主题变量配合 |
| 路由 | vue-router | ^5.2.0 | 生产用 `history` 模式（需 nginx fallback） |
| 状态 | pinia | ^4.0.2 | |
| 请求 | @vben/request（axios ^1.18.1 封装） | — | 已内置 401 刷新、错误提示、上传器 |

### 6.2 服务端

| 项 | 选择 | 说明与理由 |
| --- | --- | --- |
| 运行时 | Node 24（LTS 线） | 与前端同仓，类型可共享 |
| 框架 | **NestJS 11 + Fastify 适配器** | Guard/Decorator 与"权限码"天然映射（一个 `@RequirePermission('proto:prototype:publish')` 装饰器 + 全局 Guard 就完成接口层校验）；`@nestjs/swagger` 从装饰器生成接口文档，从根上消除"文档手写、实现漂移"；备选为 Fastify + TypeScript 手写，代价是路由/校验/OpenAPI/依赖注入都要自己搭 |
| ORM/迁移 | **Prisma** | schema 即迁移源，类型安全；备选 Kysely（更轻但要手写迁移）、TypeORM（装饰器风格但迁移体验较弱） |
| 数据库 | PostgreSQL 17（本机 Homebrew 已装，库 `protohub` 已存在且为空） | 用 `timestamptz`、`jsonb`、部分索引 |
| 认证 | JWT（access 短效内存态 + refresh HttpOnly Cookie） | 与 vben 前端预期完全对齐，见权限模型设计文档 §5 |
| 密码哈希 | argon2id | 优于 bcrypt，Node 侧 `argon2` 包 |
| zip 解压 | **yauzl** | 流式、可设 `validateEntrySizes` 防 zip bomb；`adm-zip` 会把整包读进内存（100MB 包不可接受）；`archiver` 用于「打包下载」场景（生成 zip） |
| HTML 改写 | **cheerio**（vben catalog 内已有 `^1.2.0`） | 解析并改写 HTML 属性，避免正则硬改 |
| CSS 改写 | **postcss** + `postcss-value-parser` | 改写 `url(/...)`，避免正则误伤 |
| 日志 | pino（NestJS 内置 logger 对接） | 结构化 JSON，便于检索 |
| 上传 | `@fastify/multipart` 流式落盘 | 不把 100MB 读进内存 |

### 6.3 运维

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 进程管理 | pm2（`fork` 模式，单实例） | 本机无 Docker，与用户选择一致；任务表驱动使后续可平滑扩多实例 |
| 反向代理 | nginx（需 `http_auth_request_module`，用 `nginx -V` 确认） | 承担静态直出、TLS、限速、SPA fallback |
| 备份 | `pg_dump` 定时 + 产物目录快照 | 产物量大时改为对象存储版本化 |

## 8. 核心流程

### 8.1 登录与鉴权

```
用户        管理台(vben)               Node(auth)                 PG
 │  账号密码 ─▶ POST /api/auth/login                                
 │             │ ─────────────────────▶ 校验 argon2 ──────────────▶ sys_user
 │             │                       签发 accessToken(2h, 内存)
 │             │                       签发 refreshToken(7d) ▶ Set-Cookie(HttpOnly)
 │             │ ◀── {accessToken} + Set-Cookie
 │             │ 并行 GET /user/info、GET /auth/codes、GET /menu/all
 │             │ ◀── 用户信息 / 权限码数组 / 菜单树
 │             │ 前端生成动态路由并落到侧边栏
 │  ◀── 进入工作台
```
- accessToken 有效期内所有接口带 `Authorization: Bearer <token>`；过期返回 **401**，前端拦截器自动调 `/auth/refresh` 并重放原请求（这是 vben 既有行为，后端必须按此语义返回状态码）。
- 权限码**不缓存在 token 里**，每次请求由 Guard 查库（带进程内 30 秒 LRU 缓存），以保证"改权限即时生效"。

### 8.2 上传发布（核心链路）

```
① 前端：填写/选择 归属项目 与 原型（名称+编码，编码可留空自动生成）→ 选 zip
   → POST /api/releases (multipart：project 或 projectId，prototype 或 prototypeId，file)
② 服务端：流式落临时文件 → 轻校验（大小/魔数/条目数/预估解压体积）
   ├─ 不合格 → 立即 4xx + 可读原因（前端展示在抽屉错误区）
   └─ 合格   → 建 proto_upload_task(status=processing) → 202 返回 taskId
③ 前端：轮询 GET /api/upload-tasks/{taskId}（1s 间隔，最多 120 次）
④ Worker：解压到临时目录 → 安全校验(路径穿越/符号链接/单文件与总量上限)
   → 脱壳(去掉 zip 里多余的外层目录) → 探测入口 → 路径改写 → 生成 manifest
   → 移到 releases/{projectId}/{prototypeId}/{releaseId}/
   → 事务写 proto_release + 更新 prototype.current_release_id/status=published
   → task=success
⑤ 前端：拿到 releaseId 与访问地址 → 抽屉切到"发布成功"态，展示链接与「立即访问/复制」
   失败：展示错误码与原因 + 「查看发布报告」，可重试（复用同一 task 重跑）
```
- 去重：新包内容哈希与**该原型**当前版本一致时，返回"内容未变化"提示，允许强制发布（避免误以为没生效）。去重范围是原型，不是项目——同一份 zip 发给两个原型是正常需求。
- 原型与项目在首次发布时一并创建（同一事务），因此"新建项目 + 建原型 + 发布"是一次操作，不会留下空壳。
- 详见 [原型发布与访问机制.md](./原型发布与访问机制.md)。

### 8.3 原型访问鉴权（三档）

```
浏览器 GET /p/crm/crm-p01/            nginx                          Node /api/access/check
        │                              │                                    │
        └─────────────────────────────▶ auth_request ─────────────────────▶ 用两段 code 定位原型
                                                                            ├ public → 200
                                       ◀─ 2xx 放行 ─────────────────────────┤ password → 校验该原型的解锁 cookie
                                       │                                    │   ├ 有效 → 200
                                       │                                    │   └ 无效 → 401
                                       │                                    └ member → 校验登录态 + 项目可见性
                                       │                                        ├ 有 → 200
                                       │                                        └ 无 → 403
   ┌── 200 → alias 返回该原型当前版本的目录（nginx 直出）
   ├── 401 → error_page 跳「请输入访问密码」页（POST /api/access/{项目}/{原型}/unlock）
   └── 403 → error_page 跳「需要登录/无权限/已下架」页（含去登录入口）
```

### 8.4 版本回滚

```
在原型详情的版本列表点「回滚到 v3」→ POST /api/prototypes/{id}/rollback {releaseId}
→ 事务：prototype.current_release_id = v3 ; 写 proto_release_event(rollback, from=v5, to=v3)
→ 前端刷新列表；访问链接不变，下次请求即服务 v3
```
不需要重新上传、不复制文件。**回滚只影响这一个原型的链接**，同项目下其它原型不受影响。旧版本默认保留（删除策略见发布机制文档 §4.3）。

### 8.5 权限校验（三层）

| 层 | 位置 | 作用 | 拦截表现 |
| --- | --- | --- | --- |
| 菜单层 | `/menu/all` 只下发有权访问的菜单 | 看不到入口 | 菜单不出现 |
| 页面层 | 路由 `meta.authority` + `meta.menuVisibleWithForbidden` | 直接输 URL 也进不去 | 跳 403 页 |
| 接口层 | 全局 Guard 校验 `@RequirePermission(code)` | 前端绕过也无效 | 403 + 可读原因 |
| 数据层 | `data_scope` + `proto_project_member` | 只能看到自己范围内的项目 | 列表过滤 / 单条 403 |

| --- | --- | --- | --- |
| D-01 | 前端基座用 vben-admin 5.7.0 的 `web-antd` 变体，单应用 | 用 web-ele / web-naive；自建 Vue 工程 | 图片 UI 是 antd 观感；代价：antd 4.x 生态，无法用 elem-plus 组件 |
| D-02 | `preferences.app.accessMode = 'backend'`，菜单与路由由后端下发 | `frontend`（前端写死路由+角色过滤） | 用户要"能配置角色与权限"，写死路由无法运营；代价：必须维护 `sys_menu` 与 views 路径约定 |
| D-03 | 服务端 NestJS 11 + Fastify 适配器 | Fastify+TS 手写；Koa；Egg | Guard/装饰器直接映射权限码；`@nestjs/swagger` 生成接口文档消除漂移；代价：框架约定较重，启动略慢 |
| D-04 | ORM 用 Prisma | Kysely；TypeORM | 迁移与类型安全；代价：引入 codegen 步骤 |
| D-05 | 生产由 nginx 直出静态原型，权限用 `auth_request` 交 Node 决策；开发期退化为 Node 直出 | Node 全量代理静态文件 | 性能与部署简单；代价：需 nginx 编译含 auth_request 模块，且两套放行路径要保证行为一致（靠共用决策函数） |
| D-06 | 访问控制三档 `public`/`password`/`member`，项目级配置 | 仅公开；仅登录 | 覆盖对外分享/内部评审/保密三种真实场景（用户已确认） |
| D-07 | 密码档令牌为 HMAC 签名 Cookie，签名内容含 `项目编码 + 原型编码 + 策略版本号 + 过期时间` | 会话表存令牌；JWT | 无状态、免查库；**改密码时策略版本号 +1 → 该原型所有旧令牌立即失效**；Cookie 名用原型 ID（`proto_access_p{id}`）避免两段编码拼接歧义 |
| D-08 | 存储抽象 `StorageAdapter`，v1 只实现本地磁盘，接口预留 S3/MinIO | 直接写本地路径；直接上 MinIO | 避免二次搬迁；代价：多一层接口与 key 规范化 |
| D-09 | 版本目录不可变，当前版本由 DB 指针 `current_release_id` 决定 | 用 `current` 软链接；直接覆盖目录 | 回滚是毫秒级 DB 操作且并发安全；代价：磁盘占用增长，需要 GC |
| D-10 | 上传采用"同步轻校验 + 异步解压任务 + 前端轮询" | 全同步（请求内解压完） | 100MB 解压耗时不可控，同步会撞网关/axios 超时；代价：多一个任务表与轮询接口 |
| D-11 | 发布时把 HTML/CSS 里的根绝对路径改写为 `/p/{项目编码}/{原型编码}/` 前缀，默认开、可关 | 不改写，靠文档要求产品经理自己改；要求用相对路径 | 直接消灭"白屏"最高频原因；代价：改写可能引入意外，故只改 HTML/CSS 属性与 CSS `url()`，不碰 JS，并输出改写条数报告 |
| D-12 | 缓存：HTML `no-store`，其余资源 `no-cache` + ETag | 资源长缓存（max-age=1y） | 保证"改密码/切版本/下架"立即生效优先；原型资源总量小，强校验成本可接受。见发布机制文档 §7 |
| D-13 | 无权限的菜单可配置为"可见但点击进 403" | 直接隐藏 | 让使用者知道功能存在并去申请权限（vben 原生支持 `meta.menuVisibleWithForbidden`） |
| D-14 | 项目编码与原型编码**创建后均不可修改** | 允许改并做 301 跳转 | 编码即访问路径，改编码等于换链接；需要新编码时改为「新建原型」 |
| D-15 | 数据权限用 `data_scope(all/own/member)` + `proto_project_member` 表，**范围停在项目层** | 细化到原型级授权；引入部门/项目组实体 | 项目内原型随项目一起可见，避免"同一项目的原型只有部分人能看到"这种难解释的状态；团队实体列为待决 Q-1 |
| D-16 | 部署 pm2 `fork` 单实例 + nginx + 本机 PG；发布任务由 DB 任务表驱动 | pm2 `cluster` 多实例直接起步 | 单实例省心；任务表驱动使多实例化只需换调度方式，不改业务代码（用户已确认裸机部署） |
| D-17 | 前端与后端同仓 monorepo（`apps/admin` + `apps/server` + `packages/shared`） | 分仓 | 契约类型一处定义两端引用，减少字段对不上；代价：仓库体积与 CI 复杂度上升 |
| D-18 | **三级模型：项目 → 原型 → 版本**；项目是容器，原型是分享与鉴权的最小单位 | 两级（项目即分享单位，用"多版本"承载不同原型） | 用户明确"每个项目会发布很多个 HTML 原型"；把不同原型塞进一个版本序列会导致回滚语义混乱（回滚 A 会连带 B）；代价：多一层表与页面层级 |
| D-19 | 访问路径 `/p/{项目编码}/{原型编码}` | `/p/{原型编码}`（原型编码全局唯一） | 两级路径能看出归属、原型编码只需项目内唯一（随机码更短）、与管理台路由不冲突；代价：路径长一段，且要给 `/p/{code}` 单段路径单独返回 404 |
| D-20 | 两个编码都**可自定义**，留空则自动生成：项目＝`p-` + 8 位 base36 随机；原型＝`{项目编码}-p{两位序号}` | 必填手填；全部随机 | 降低创建摩擦（产品经理不用为每个原型想名字）；代价见 D-21 下方的枚举风险 |
| D-21 | **访问策略（公开/密码/仅成员）从项目层下移到原型层** | 留在项目层；或项目层默认 + 原型层覆盖 | 同一项目下不同原型常需要给不同的人看（登录页给客户看、内部流程页只给内部）；代价：批量设置策略时需要逐条操作，P1 加"批量设置"入口 |
| D-22 | 项目状态（已归档/已发布/草稿）**由原型聚合派生，不落库**；原型状态落库 | 项目状态落库并随原型发布/归档维护 | 避免"项目状态"与"原型状态"两处真相漂移（维护它需要在每次原型发布/归档时同步更新项目，是 bug 温床）；代价：列表按状态筛选需要 EXISTS 子查询 |

## 11. 风险与对策

| 编号 | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R-1 | 恶意/异常 zip（zip bomb、路径穿越、符号链接） | 磁盘打满、任意文件写入 | 条目数 ≤5000、单文件 ≤200MB、解压总量 ≤500MB、压缩比阈值；路径规范化后必须在目标根内；拒绝符号链接；见发布机制文档 §2 |
| R-2 | 磁盘增长不可控 | 服务不可用 | 版本保留策略（每项目保留最近 N 个 + 保留最近 M 天）、GC 定时任务、容量告警阈值 |
| R-3 | 原型白屏（路径/base 标签/外链依赖） | 用户认为平台坏了 | 发布时改写 + 发布报告列出改写条数与可疑项（如 `<base>`、外链 CDN）+ 发布失败原因码可读 |
| R-4 | 权限变更不即时生效 | 安全漏洞 | 鉴权端口径唯一在 Node 且每次查库（30s LRU）；nginx 侧只对静态文件做缓存，不对鉴权决策做缓存 |
| R-5 | 大文件上传中断/超时 | 发布失败体验差 | 流式落盘 + 断点不续传但可重试；nginx `client_max_body_size 110m`；P1 加分片续传 |
| R-6 | 单实例成为并发瓶颈 | 发布会排队 | 任务表驱动；若压力大，加一个实例只跑 worker（同一 DB 队列，行级锁抢占） |
| R-7 | 原型内含表单提交/外链埋点被误当平台能力 | 数据泄露误解 | 平台不代理任何原型内的第三方请求；在发布页与访问记录页明示"原型为静态演示，不含后端能力" |
| R-8 | 访问记录写入量拖慢访问 | 静态访问变慢 | 只记录入口文档级请求；异步批量写库；写失败只落本地日志，绝不影响文件返回 |
| R-9 | 自动生成的编码**可被枚举**（`crm-p01`、`crm-p02`…），他人可猜到未公开的原型地址 | 保密原型的"隐私"被削弱（虽然仍有密码/成员档拦截） | ① 门面页对"不存在"与"无权限"返回**同一形态**，不泄露存在性；② 不存在/未发布的编码同样计入限速，避免被批量探测；③ 编码一旦自定义即不可枚举；④ 对外保密建议在创建时手填一个无规律的编码（界面上给出提示）。是否默认改为随机编码见 §12 Q-7 |
| R-10 | 一个项目下原型过多（几十个）导致详情页难以浏览 | 可用性下降 | 原型列表默认按最近更新排序 + 支持关键字搜索与状态筛选；超过 20 个时列表分页；"批量设置访问策略"列入 P1 |
