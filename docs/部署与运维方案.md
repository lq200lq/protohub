启动：

```bash
pnpm install
pnpm --filter @protohub/db exec prisma migrate dev      # 建表（protohub 库已就绪）
pnpm --filter @protohub/db exec prisma db seed           # 权限/角色/菜单/首个超管
pnpm --filter @protohub/server start:dev                 # 监听 127.0.0.1:3100
pnpm --filter @protohub/admin  dev                       # 监听 127.0.0.1:5671，/api 代理到 3100
```

开发环境两个要点：

1. 访问管理台用 **`http://127.0.0.1:5671`**，不要用 `localhost:5671`。`localhost` 会同时解析到 `::1` 与 `127.0.0.1`，如果同端口上有别的进程占了其中一族地址，会请求到别人的服务上（排查起来极费时间）。
2. 开发期 `PUBLIC_BASE_URL=http://127.0.0.1:3100`（原型链接直指 Node）。这不是笔误：管理台在 5671、原型站点在 3100，是两个端口。Cookie 不区分端口，所以登录态在两者间共享，member 档在开发环境同样可测。

## 3. pm2 配置

`/opt/protohub/deploy/pm2/ecosystem.config.cjs`：

```js
module.exports = {
  apps: [
    {
      name: 'protohub-api',
      cwd: '/opt/protohub/server',
      script: 'dist/main.js',

      // fork 单实例（决策 D-16）：发布任务由 DB 任务表驱动，
      // 将来要多开只需复制这段并改 name/实例数，不需要改业务代码。
      exec_mode: 'fork',
      instances: 1,

      node_args: '--max-old-space-size=1024',
      max_memory_restart: '1200M',
      autorestart: true,
      max_restarts: 10,
      restart_delay: 3000,

      // 优雅退出：收到 SIGINT 时停止拉取新任务、把进行中的任务放回 pending
      kill_timeout: 20000,
      shutdown_with_message: true,

      env: {
        NODE_ENV: 'production',
        PORT: '3100',
        HOST: '127.0.0.1',
        STORAGE_ROOT: '/opt/protohub/storage',
        SERVE_STATIC: 'nginx',
        PUBLIC_BASE_URL: 'https://proto.company.com',
      },
      // 密钥与 DATABASE_URL 走系统环境变量或 --env-file，不写进这个文件

      error_file: '/var/log/protohub/api.error.log',
      out_file: '/var/log/protohub/api.out.log',
      merge_logs: true,
      time: true,
    },
  ],
};
```

```bash
pm2 start /opt/protohub/deploy/pm2/ecosystem.config.cjs
pm2 save
pm2 startup            # 生成开机自启命令并执行它
pm2 install pm2-logrotate
pm2 set pm2-logrotate:max_size 50M
pm2 set pm2-logrotate:retain 14
pm2 set pm2-logrotate:compress true
```

**为什么用 fork 单实例而不是 cluster**：发布任务的处理循环是"从任务表取一条、串行处理"，多实例在单机上也只会让磁盘 IO 互相抢；而 `SERVE_STATIC=nginx` 已经把静态流量从 Node 剥离了，Node 的负载主要是管理台 API（QPS 很低）。用 cluster 反而引入"多进程抢同一任务"的复杂度（虽然 `SKIP LOCKED` 能处理，但没必要）。

**优雅退出**：Node 侧监听 `SIGINT`，收到后停止 worker 循环、把 `processing` 状态的任务改回 `pending`（带 `retry_count + 1`），然后关闭 DB 连接。`kill_timeout: 20000` 给足这个时间。否则重启时进行中的发布会永远卡在 `processing`（虽然有 10 分钟巡检兜底，但要等）。

## 4. 日志

| 日志 | 位置 | 轮转 |
| --- | --- | --- |
| Node 应用日志 | `/var/log/protohub/api.{out,error}.log`（pino JSON） | pm2-logrotate，50MB × 14 份，压缩 |
| nginx access | `/var/log/nginx/protohub.access.log` | logrotate 系统默认（14 天），格式见 §5 |
| nginx error | `/var/log/nginx/protohub.error.log` | 同上 |
| 发布任务失败 | 落库 `proto_upload_task`（**不只靠日志文件**） | 90 天 |
| 访问记录 | 落库 `proto_access_log` | 180 天 |

**日志必须带 `traceId`**：`/api/access/check` 与所有业务接口在响应头回传 `X-Trace-Id`，nginx access log 记录它（`trace=$http_x_trace_id`）。用户报障时让他提供该值，直接在日志里 grep 一条链路，不必靠时间猜。

**静态访问的日志量要控制**：`/p/` 下的每个资源请求都会进 nginx access log。若某原型对外引流较大，日志会膨胀。一期先用**全量日志**（便于排查白屏）。容量增长后改用条件日志——只记"入口文档"与"非 2xx/3xx"：

```nginx
# 需要与 §5 顶部的 map 放在一起
map $request_uri $proto_is_entry { ~*\.(html?|htm)($|[?#]) 1; default 0; }
map $status      $proto_is_error { ~^[23]                 0; default 1; }

# 拼成 "是否入口:是否错误"，只有"非入口且成功"不记
map "$proto_is_entry:$proto_is_error" $proto_loggable {
    "0:0"   0;
    default 1;
}

# 然后替换 server 内的 access_log 一行：
# access_log /var/log/nginx/protohub.access.log protohub if=$proto_loggable;
```

## 5. nginx 完整配置

`/etc/nginx/conf.d/protohub.conf`（`conf.d` 被包含在 `http{}` 内，所以 `map`/`upstream`/`limit_req_zone` 可写在这里）：

```nginx
# ============================================================ 上游与变量

upstream protohub_api {
    server 127.0.0.1:3100;
    keepalive 32;
}

# 从请求 URI 提取两段编码（访问路径形如 /p/{项目编码}/{原型编码}/...）
# 用 $1 而不是命名捕获：map 的结果值只保证支持 $1..$9，"命名捕获当结果值"并非文档化行为
map $request_uri $proto_project_code {
    ~^/p/([a-z0-9]+(?:-[a-z0-9]+)*)/   $1;
    default                           "";
}
map $request_uri $proto_prototype_code {
    ~^/p/[a-z0-9]+(?:-[a-z0-9]+)*/([a-z0-9]+(?:-[a-z0-9]+)*)   $1;
    default                                                     "";
}

# 按扩展名决定缓存策略（决策 D-12：HTML 不缓存、其余强校验）
# 注意 $request_uri 含 query string，所以结尾要容忍 ? 与 #
#
# 第二条（目录写法）是 M4-T4/T5 实测补的（计划 §9.2 DEV-31）：入口链接 /p/{项目}/{原型}/ 发的是
# 版本目录的默认文档 index.html，可 URI 里没有出现扩展名，只写第一条时它落到 default "no-cache"——
# 而这条恰恰是用户收藏与转发的那一条链接。Node 直出侧的 isHtmlUri 同两条判据，单测逐条对这张表。
map $request_uri $proto_cache_control {
    ~*\.(html?|htm)($|[?#])    "no-store";
    ~*/($|[?#])                "no-store";
    default                    "no-cache";
}

# 安全兜底：只接受"releases/{项目ID}/{原型ID}/{版本ID}"形状的目录名，
# 任何空值或异常值都落到一个不存在的目录，避免 root 退化成存储根目录
map $upstream_http_x_proto_release_dir $proto_release_dir {
    ~^releases/[0-9]+/[0-9]+/[0-9]+$   $upstream_http_x_proto_release_dir;
    default                           "_invalid";
}

log_format protohub '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" "$http_user_agent" '
                    'rt=$request_time urt=$upstream_response_time trace=$http_x_trace_id';

limit_req_zone $binary_remote_addr zone=proto_unlock:10m rate=10r/m;
limit_req_zone $binary_remote_addr zone=proto_login:10m  rate=30r/m;
limit_req_zone $binary_remote_addr zone=proto_api:10m    rate=50r/s;

# ============================================================ HTTP → HTTPS

server {
    listen 80;
    server_name proto.company.com;
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 301 https://$host$request_uri; }
}

# ============================================================ 主站

server {
    listen 443 ssl;
    http2 on;
    server_name proto.company.com;

    ssl_certificate     /etc/nginx/ssl/proto.company.com.fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/proto.company.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;

    access_log /var/log/nginx/protohub.access.log protohub;
    error_log  /var/log/nginx/protohub.error.log warn;

    # 上传体积必须 ≥ 后端 MAX_UPLOAD_BYTES(100MB) + 余量
    client_max_body_size   110m;
    client_body_timeout    300s;
    server_tokens          off;

    gzip              on;
    gzip_comp_level   5;
    gzip_min_length   1024;
    gzip_proxied      any;
    gzip_types        text/plain text/css text/xml application/json
                      application/javascript application/xml+rss
                      image/svg+xml application/font-woff2;
    # 若已装 brotli 模块，可加：brotli on; brotli_types ...;

    # ------------------------------------------------ 管理台 SPA
    root  /opt/protohub/admin/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    # 构建产物文件名带内容哈希 → 长缓存
    # 注意：location 内一旦出现 add_header，会覆盖 server 级别的 add_header（见 §5.1）
    location ^~ /assets/ {
        add_header Cache-Control "public, max-age=2592000, immutable" always;
        include    /opt/protohub/deploy/nginx/security-headers.conf;
    }

    # ------------------------------------------------ 后端 API
    location /api/ {
        limit_req zone=proto_api burst=100 nodelay;

        proxy_pass         http://protohub_api;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_set_header   Connection        "";
        proxy_read_timeout 180s;
        # 默认 proxy_request_buffering on：nginx 先收完整个 body 再转给 Node，
        # 既能抵御慢客户端，又天然把"上传中"与"处理中"分成两段（与我们前端的双段进度一致）。
    }

    # 登录接口限速（第二层，应用层另有 username+ip 失败锁定）
    # 注意：办公室 NAT 下多用户共享出口 IP，速率不能压得太死
    location = /api/auth/login {
        limit_req  zone=proto_login burst=10 nodelay;
        proxy_pass http://protohub_api;
        include    /opt/protohub/deploy/nginx/proxy-common.conf;
    }

    # 解锁接口单独限速（防暴力猜密码）
    location ~ ^/api/access/[a-z0-9-]+/unlock$ {
        limit_req  zone=proto_unlock burst=5 nodelay;
        proxy_pass http://protohub_api;
        include    /opt/protohub/deploy/nginx/proxy-common.conf;
    }

    # ------------------------------------------------ 原型访问
    # 访问决策子请求（内部，不可从外部访问）
    location = /__proto_auth {
        internal;
        proxy_pass         http://protohub_api/api/access/check;
        proxy_pass_request_body off;
        proxy_set_header   Content-Length  "";
        proxy_set_header   X-Original-URI  $request_uri;
        proxy_set_header   Cookie          $http_cookie;
        proxy_set_header   X-Real-IP       $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   Host            $host;
    }

    # 门面页（由 error_page 转入；受众可能是外部客户，故不走 SPA）
    location @proto_gate_password {
        proxy_pass http://protohub_api/api/access/gate?project=$proto_project_code&prototype=$proto_prototype_code&code=401&reason=$proto_reason&from=$request_uri;
        include    /opt/protohub/deploy/nginx/proxy-common.conf;
    }
    location @proto_gate_forbidden {
        proxy_pass http://protohub_api/api/access/gate?project=$proto_project_code&prototype=$proto_prototype_code&code=403&reason=$proto_reason&from=$request_uri;
        include    /opt/protohub/deploy/nginx/proxy-common.conf;
    }
    location @proto_gate_notfound {
        proxy_pass http://protohub_api/api/access/gate?project=$proto_project_code&prototype=$proto_prototype_code&code=404&from=$request_uri;
        include    /opt/protohub/deploy/nginx/proxy-common.conf;
    }

    # 原型站点：/p/{项目编码}/{原型编码}/... → 版本目录（由 auth_request 的响应头告知目录）
    location ^~ /p/ {
        auth_request       /__proto_auth;
        auth_request_set   $proto_reason      $upstream_http_x_proto_reason;

        error_page 401 = @proto_gate_password;
        error_page 403 = @proto_gate_forbidden;
        error_page 404 = @proto_gate_notfound;

        # 少一个尾斜杠 → 301（必须写在块内，理由见本节末的修订说明；$1/$2 取原始 URI，不用那两个 map）
        if ($request_uri ~ ^/p/([^/?#]+)/([^/?#]+)$) {
            return 301 /p/$1/$2/;
        }

        # 剥掉 /p/{项目编码}/{原型编码} 两段前缀，剩下的是产物内相对路径
        rewrite ^/p/[^/]+/[^/]+/?(.*)$ /$1 break;

        # 版本目录来自 map 白名单（$proto_release_dir 由 config 顶部的 map 定义，
        # 只接受 releases/{数字}/{数字}/{数字}，异常值落到 _invalid，绝不退化为存储根）
        root /opt/protohub/storage/$proto_release_dir;

        # 目录写法发默认文档；与顶部 map 的"目录也算 HTML"那条是一对
        index  index.html;

        add_header Cache-Control $proto_cache_control always;
        include    /opt/protohub/deploy/nginx/security-headers.conf;

        # 兜底：不对外提供点文件（清单副本已在 manifests/ 目录外，此处仅防御）
        location ~ /\. { deny all; }
    }
}
```

> **少尾斜杠的 301 与单段 404 都写在 `location ^~ /p/` 里面（M4-T4/T5 实测修正，计划 §9.2 DEV-31）**
>
> 原设计把这两条放在外面：
>
> ```nginx
> # 已删除：这两条永远不会执行
> location ~ ^/p/[^/]+/[^/]+$ { return 301 /p/$proto_project_code/$proto_prototype_code/; }
> location ~ ^/p/[^/]+$       { return 404; }
> ```
>
> 而 §5.1 自己记过的那条优先级规则正好把它杀了：**`^~ /p/` 命中后 nginx 不再尝试任何正则
> location**（同一节里"deny 点文件必须嵌套写进 `/p/` 内部"就是同一条规则的另一个后果）。于是
> `/p/{项目}/{原型}` 这个手敲/转发时最常见的形态会走进 `/p/` 块、被那条 `rewrite` 变成 `/`，
> 用户看到的是默认文档而不是 301——看起来"能打开"，但产物里 `assets/app.js` 这类相对引用会按
> `/p/{项目}/assets/app.js` 去取，结果是白屏。
>
> 现在的写法（块内 `if` + `return`，`if` 配 `return` 是官方认可的安全用法）：
>
> ```nginx
> if ($request_uri ~ ^/p/([^/?#]+)/([^/?#]+)$) {
>     return 301 /p/$1/$2/;
> }
> ```
>
> 单段 `/p/{项目编码}` 则**不需要**任何规则：它同样落进 `^~ /p/`，`auth_request` 打到
> `/api/access/check`，服务端解析不出两段编码就返回 `404 + X-Proto-Reason: NOT_FOUND`，
> `error_page 404` 直接接住给出门面页——走不到静态处理器，也就不会被 `location /` 的 SPA
> `try_files` 兜成管理台的 404 页。
>
> Node 直出侧同口径：`/p/*` 一条通配路由吃下全部形状（Fastify 的 `/p/:a/:b/*` 不吃"通配段为空"
> 的两种 URL，那样会掉进 Nest 的默认 404，返回一枚 JSON 信封），解析不出一律门面页 404，
> 少尾斜杠一律 301。

### 5.1 nginx 容易踩的坑（本配置已规避，改动时注意）

> **验证状态**：本配置**尚未用 `nginx -t` 实测**（开发机未安装 nginx，生产环境的 nginx 版本与模块也不确定）。首次部署时必须先在目标机器上 `nginx -t` 通过再 reload，并把 `with-http_auth_request_module`、`http2 on`（1.25.1+ 才支持该写法，旧版需 `listen 443 ssl http2;`）、`limit_req_zone` 的语法差异一起核对。这三处都是版本相关的，不要照抄后就认为是已验证的。

| 坑 | 说明 | 本配置的处理 |
| --- | --- | --- |
| `add_header` 不继承 | 只要某个 location 里写了 `add_header`，**server 级别的 `add_header` 就不会继承到该 location**（HSTS、X-Frame-Options 等会静默消失） | 安全头抽到 `security-headers.conf` 并在每个设置了 `add_header` 的 location 里 `include` |
| 正则 location 与 `^~` 的优先级 | `^~ /p/` 命中后**不再尝试正则 location**（前缀匹配里只有 `^~` 与 `=` 有这个效力），所以"deny 点文件"的正则必须写在 `/p/` 内部 | 已写成 `location ^~ /p/` 内的嵌套 `location ~ /\.`；原先挂在 server 级的两条正则（无尾斜杠 301、单段 404）会被 `^~` 静默吞掉，已删除并在 §5 的修订说明里换成 `if` + `error_page` |
| `auth_request` 拿不到数据库里的版本目录 | nginx 无法查库决定服务哪个版本 | 由决策接口在 200 响应里回传 `X-Proto-Release-Dir`，nginx 侧用**白名单 map** 取值作为变量 `root` |
| 变量 `root` 为空会退化为存储根目录 | 若直接写 `root /opt/protohub/storage/$upstream_http_x_proto_release_dir`，一旦该头缺失（后端 bug、上游异常、非 200 响应残留），`root` 变成 `/opt/protohub/storage/`，请求就会命中 `manifests/`、`trash/`——**这是一次目录泄露** | 用 map 做形状白名单（`^releases/[0-9]+/[0-9]+/[0-9]+$`），异常值一律落到不存在的 `_invalid`，配合 `ErrorDocument` 语义直接 404 |
| `rewrite` 必须剥掉**两段**前缀 | 三级模型下访问路径有两段编码，只剥一段会把原型编码当成产物内的目录名（`/p/crm/crm-p01/assets/x.js` → `crm-p01/assets/x.js` → 404 白屏） | `rewrite ^/p/[^/]+/[^/]+/?(.*)$ /$1 break;`，且 `?` 让 `/p/a/b`（无尾斜杠）也能落到 `/` 走 index |
| 单段 `/p/{code}` 不能落到 SPA | `location /` 的 `try_files … /index.html` 会把它当管理台路由，用户看到的是管理台的 404 页而不是"链接无效" | 由 `^~ /p/` 内的 `auth_request` 拦住：服务端解析不出两段编码就回 `404 + X-Proto-Reason: NOT_FOUND`，`error_page 404` 接住给门面页。**不要**再在 server 级加 `location ~ ^/p/[^/]+$ { return 404; }`——它永远匹配不到（见上一条），加了等于没加 |
| 目录写法也是 HTML | `/p/{项目}/{原型}/` 正是分享与收藏的那条链接，`rewrite` 后由 `index index.html;` 换成 `index.html`，但缓存 map 用的是**原始 `$request_uri`**，它没有 `.html` 扩展名。原来只写了扩展名一条，这条链接会被打上 `no-cache`，改了密码、换了版本仍可能吃到旧页面 | map 增加 `~*/($|[?#])  "no-store"` 一条；与 `static-mime.ts` 的 `isHtmlUri()` 逐字符同形，两边必须一起改 |

> 第 4 条是本配置里最容易被后续改动破坏的一处。任何人把 `root` 改回直接使用 `$upstream_http_*` 都等于打开了目录泄露，改动前请先读这一行。

`security-headers.conf`：

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options    "nosniff" always;
add_header Referrer-Policy           "strict-origin-when-cross-origin" always;
# 管理台不开放被第三方 iframe 嵌入
add_header X-Frame-Options           "SAMEORIGIN" always;
```

`proxy-common.conf`：

```nginx
proxy_http_version 1.1;
proxy_set_header   Host              $host;
proxy_set_header   X-Real-IP         $remote_addr;
proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header   X-Forwarded-Proto $scheme;
proxy_set_header   Connection        "";
```

> 注意：`X-Frame-Options: SAMEORIGIN` 对**门面页**是合适的，但**原型内容**若需要被内网 wiki 通过 iframe 嵌入就会被拦。是否放开由业务决定，默认不放（更安全）。这与"member 档在 iframe 里不可用"的 SameSite 限制是两件独立的事（见发布机制文档 §5.4）。

配置校验与生效：

```bash
nginx -t && nginx -s reload
```

## 6. 数据库初始化与备份

### 6.1 初始化

```bash
# 1) 建独立库账号（不用 postgres 超级用户跑业务）
sudo -u postgres psql -c "CREATE ROLE protohub LOGIN PASSWORD '<strong>';"
sudo -u postgres psql -c "CREATE DATABASE protohub OWNER protohub ENCODING 'UTF8';"
sudo -u postgres psql -d protohub -c "CREATE EXTENSION IF NOT EXISTS pgcrypto;"   # 预留

# 2) 迁移与种子（由部署脚本执行，失败即中止部署）
cd /opt/protohub/server
pnpm --filter @protohub/db exec prisma migrate deploy
pnpm --filter @protohub/db exec prisma db seed      # 幂等，可重复执行

# 3) 首个超级管理员（幂等；已存在任一 super_admin 则跳过）
node dist/scripts/seed-admin.js --username admin
# 输出：created user "admin" with initial password: Xy7#k2Pq...(仅打印一次)
```

`deploy/init/` 下同时保留一份**纯 SQL 版**（`01_schema.sql` 由 `prisma migrate diff` 生成、`02_seed.sql`）用于没有 Node 环境时的应急建库，但**日常只走 Prisma 迁移**，避免两套源漂移。

### 6.2 备份

`/opt/protohub/deploy/backup.sh`（crontab：`30 2 * * *`）：

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%F)
DEST=/backup/protohub

# 1) 数据库（自定义格式，支持并行恢复与选择性恢复）
pg_dump -Fc -h 127.0.0.1 -U protohub protohub > "$DEST/pg/protohub-$STAMP.dump"

# 2) 产物存储（只增不减，增量同步即可）
rsync -a --delete-after /opt/protohub/storage/releases/ "$DEST/storage/releases/"
rsync -a --delete-after /opt/protohub/storage/manifests/ "$DEST/storage/manifests/"

# 3) 保留 30 天
find "$DEST/pg" -name '*.dump' -mtime +30 -delete
```

**恢复顺序（关键）**：先恢复**产物**（`releases/` 与 `manifests/`），再恢复**数据库 dump**。原因是数据库里的 `storage_key`/`current_release_id` 是"指针"，如果先恢复库、后恢复文件，窗口期内会出现"指针指向不存在的目录"（访问 404）；反过来先铺文件再铺库，中间态只是"盘上有不被引用的目录"（无害，且 GC 会清理）。

恢复演练：每季度把最新 dump 恢复到 `protohub_restore` 库，跑一次健康检查 + 抽查 2 个项目的访问地址是否 200。**没演练过的备份不算备份**。

## 7. 监控与告警

| 指标 | 采集方式 | 阈值与动作 |
| --- | --- | --- |
| **磁盘余量**（最重要） | `df -h /opt/protohub/storage`，cron 每 5 分钟 | <20% 告警；<10% 停止接受上传（接口返回 `UPLOAD_DISK_FULL`） |
| 服务存活 | `curl -fsS http://127.0.0.1:3100/api/health`，每 1 分钟 | 连续 3 次失败 → 告警 + `pm2 restart protohub-api` |
| 发布任务积压 | `select count(*) from proto_upload_task where status in ('pending','processing')` | >10 持续 30 分钟 → 告警（可能 worker 卡死） |
| 5xx 率 | nginx access log 统计 | >1% 持续 10 分钟 → 告警 |
| 鉴权接口延迟 | `urt` 字段统计 `/__proto_auth` | P95 >50ms → 排查（正常应 <1ms，见发布机制文档 §7.1） |
| 数据库连接数 | `select count(*) from pg_stat_activity` | >80% `max_connections` → 告警 |
| 备份成功 | backup.sh 退出码 | 失败即告警 |

一期用简单 shell + cron + 邮件/企微 webhook 即可，不引入 Prometheus（规模不需要）。`/api/health/detail`（需 `system:log:list` 权限）返回 DB 连接、队列积压、磁盘余量，供人工排查。

## 9. 容量规划与 GC 运维

| 项 | 估算 | 依据 |
| --- | --- | --- |
| 数据库 | 1 年内 <1GB | 元数据 + 日志（访问日志 180 天，10 万行/年量级） |
| 产物存储 | `原型数 × 每个原型保留版本数 × 平均包体积`；例：10 个项目共 60 个原型 × 5 版本 × 平均 8MB ≈ 2.4GB | 保留策略见发布机制文档 §4.3 |
| trash 缓冲 | 建议预留 ≥ 2 × 上表产物总量 | 7 天延迟删除期内的最大占用 |
| 建议磁盘 | ≥50GB（含系统、日志、备份中转） | |

> 容量必须**按原型数**估算，不能按项目数——一个项目下有 20 个原型时总量是 20 倍关系（发布机制文档 §9 有同一条说明，两处口径必须一致）。

**GC 日常检查**：每天 GC 后打印一条 summary（删除目录数、释放字节、当前余量）。运维每周看一次该日志；若"释放字节"长期为 0 而磁盘在涨，说明保留策略没生效，需查 `KEEP_RECENT_RELEASES` 是否被调大、或原型数量是否激增。

**磁盘水位应急动作**（按顺序，逐步放狠）：

1. 清 `trash/`（跳过 7 天 TTL）：`rm -rf /opt/protohub/storage/trash/*`
2. 清 `tmp/`：`find /opt/protohub/storage/tmp -mtime +1 -delete`
3. 临时把 `KEEP_RECENT_RELEASES` 降到 2、`KEEP_MIN_DAYS` 降到 7，手工触发一次 GC
4. 排查大体积项目与原型：`du -sh /opt/protohub/storage/releases/* | sort -h`，再对该项目下钻 `du -sh /opt/protohub/storage/releases/{projectId}/*`，与项目负责人确认删除

**不做的应急处置**：不要直接删 `releases/` 下的目录——那会让数据库指针指向不存在的目录，产生大量 404 且无法自愈。删必须走 GC（它同时更新数据库标记）。

## 10. 常见故障与处置

| 现象 | 首要排查 | 常见原因 |
| --- | --- | --- |
| 原型打开白屏 | 浏览器控制台 404 的资源路径 → 该次发布的"发布报告" | 路径改写没覆盖（如 JS 里拼的路径、用了 `<base>`）；资源确实缺失 |
| 原型返回"已下架" | `select p.status, p.archived_at, j.archived_at from proto_prototype p join proto_project j on j.id = p.project_id where j.code=? and p.code=?` | 原型被归档、或它所属**项目**被归档（两者都会使链接失效，注意区分）；或 `access_mode` 与预期不符 |
| 所有原型突然 401/要求密码 | `ACCESS_TOKEN_SECRET` 是否被改动/轮换 | 改密钥会让所有已签发的解锁 Cookie 失效（预期行为，需重新输入密码） |
| 成员档一直提示"仅限内部成员"而用户已登录 | 浏览器是否带 `proto_sess` Cookie（DevTools → Application → Cookies） | Cookie 被清；或原型在 iframe 中（SameSite=Lax 不发送，见发布机制文档 §5.4） |
| 管理台接口全部 401 | pm2 日志中 JWT 校验错误；系统时间是否漂移 | 密钥变更；或服务器时间偏差导致 JWT 判定过期 |
| 发布任务一直 `processing` | `select id,stage,started_at from proto_upload_task where status='processing'` | worker 已死（重启恢复）或磁盘写满 |
| 上传报 413 | nginx `client_max_body_size` 与 `MAX_UPLOAD_BYTES` | 两处阈值不一致 |
| nginx 502 | `ss -lntp \| grep 3100` | Node 未启动 / 端口不对 / 崩溃重启中 |
| 安全头没生效 | — | 命中了 §5.1 第一个坑：某个 location 写了 `add_header` 导致不继承 |
| 磁盘满 | `du -sh /opt/protohub/storage/*` | 见 §9 应急动作 |

## 11. 部署流程（每次发版）

```bash
# 构建（可在本机或 CI 完成，产物拷到服务器）
pnpm install --frozen-lockfile
pnpm --filter @protohub/shared build
pnpm --filter @protohub/server build
pnpm --filter @protohub/admin  build        # 输出 apps/admin/dist

# 到服务器
rsync -a --delete server/dist/      /opt/protohub/server/dist/
rsync -a --delete admin/dist/       /opt/protohub/admin/dist/
# nginx / pm2 配置有变更时先同步到 /opt/protohub/deploy/ 并 nginx -t

# 数据库迁移（必须先于启动新版本，且失败即中止）
pnpm --filter @protohub/db exec prisma migrate deploy

# 重启（零停机做不到：单实例重启约 3-10 秒，期间静态原型仍由 nginx 正常服务，
# 只有管理台接口短暂不可用。这是可接受的取舍，记入平台设计方案决策 D-16。）
pm2 reload protohub-api
# 或 pm2 restart protohub-api --update-env   （环境变量有变更时）

# 验证
curl -fsS http://127.0.0.1:3100/api/health
curl -fsS -o /dev/null -w '%{http_code}\n' https://proto.company.com/
```

**发版回滚**：代码回滚用上一个 `dist/` 备份（部署脚本在覆盖前把旧 `dist/` 打包为 `dist-<时间戳>.tgz` 保留 3 份），`prisma migrate deploy` 对应的**不可回滚迁移**必须在迁移文件中注明（数据库设计 §7 的约定），遇到不可回滚迁移时回滚代码前先确认数据兼容性。
