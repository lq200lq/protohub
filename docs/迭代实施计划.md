# 迭代实施计划

> 状态：M0 ✅ M1 ✅（进行中→M2）｜ 更新：2026-10-06 ｜ 关联：[平台设计方案.md](./平台设计方案.md) §9 里程碑（本文档是它的可执行展开）

本文档是**执行权威**：说清"按什么顺序做、每步的产出与判据、什么算完成、发现偏差往哪写"。
设计权威仍在各专题文档（表结构、接口契约、权限码、页面结构），本文档**只引用不复制**它们的内容。

## 1. 这份文档怎么用

### 1.1 总目标陈述（可直接作为 Goal 的目标）

```
按 /Users/q/workspace/demospace/protoHub/docs/迭代实施计划.md 实现 ProtoHub（HTML 原型托管平台）。

规则：
1. 按 M0 → M1 → M2 → M3 → M4 → M5 顺序推进，一个阶段通过 Gate 才进下一阶段；
   不要为了"看起来更快"把多个阶段并行或跳步。
2. 每个阶段开始前，先读该阶段「必读」列出的设计文档章节；实现中出现与设计冲突的情况，
   停下来在 §9 记一条偏差，不要自行改设计或绕过。
3. 每个阶段的 Gate 必须实测通过（命令真实跑过、界面真实点过），不允许"看代码觉得没问题"。
4. 每阶段完成后回写 §9（状态行 + 偏差），并同步被推翻的设计细节到对应设计文档。
5. 范围不含部署与运维：不写 nginx / pm2 / CI / 备份 / 监控配置。
6. 不修改 packages/** 下的 vben 框架代码；不引入 §3.2 白名单之外的依赖。
```

### 1.2 分阶段目标（推荐用法）

长任务用**一个 Goal 跑完全部阶段**风险大：一次 Gate 没过就会在错误的基线上继续堆代码，而且中途要人判断的东西被吞掉。
推荐**一个阶段一个 Goal**，用下面这句 + 本文档 §5 对应小节：

```
按 docs/迭代实施计划.md §5 的「M1 权限体系与登录全链路」实现。
先读该节的必读章节与任务表，逐条实现到判据；最后跑该节 Gate 并逐项实测。
不碰 M2 及以后的内容；发现设计偏差写进 §9 而不是自行决定。
```

### 1.3 权威边界

| 内容 | 权威位置 | 本文档的处理 |
| --- | --- | --- |
| 表结构 / 字段 / 索引 | [数据库设计.md](./数据库设计.md) | 只写"要落哪张表、要对齐哪一节" |
| API 契约 / 错误码 / 分页 | [后端接口设计.md](./后端接口设计.md) | 只写"要实现哪个编号的接口" |
| 权限码取值 / 角色范围 / 认证语义 | [权限模型设计.md](./权限模型设计.md) | 只引用权限码标识符 |
| 页面 / 路由 / 组件 / 交互 | [前端设计.md](./前端设计.md) | 只写"要交付哪个页面" |
| 发布流水线 / 鉴权机制 / 缓存 | [原型发布与访问机制.md](./原型发布与访问机制.md) | 只写"要实现哪一步" |
| 部署与运维 | [部署与运维方案.md](./部署与运维方案.md) | **本期不做**，只在 §3.3 借用本地运行方式 |
| 执行顺序 / 判据 / 偏差 | **本文档** | — |

### 1.4 回写规则（每阶段必做，不是可选项）

1. 在 §9 追加一行**阶段状态**（阶段、状态、完成日期、Gate 证据）。
2. 实现期与设计不一致的地方，在 §9 的**偏差**小节点追加一条：`编号 / 设计怎么写 / 实际怎么做 / 为什么 / 已同步到哪个文档`。
   历史行**不回改**——口径变了就追加新行，这样"当初为什么这么定"永远有据可查。
3. 被推翻的设计细节（例如某接口参数名变了）**必须同步改对应设计文档**，否则文档会变成假信息；
   同步时在该设计文档里保留"原设计 + 修订说明"，不直接抹掉原设计。

### 2.2 明确不做

- **部署与运维**：nginx、pm2、TLS、备份、监控告警、CI/CD、Docker。原因见 §2.3。
- 二期功能：访问记录导出 CSV、分享二维码、原型内批注、通知、上传分片续传、批量设置策略、成员角色差异化授权。
- 三期功能：对象存储（S3/MinIO）实现、自定义域名、SSO/LDAP、多租户。

### 2.3 为什么"不做运维"不影响本期验收

设计里已经留好了开发形态：`SERVE_STATIC=node` 时由 Node 直接服务 `/p/{项目编码}/{原型编码}/*`，并且**与生产 `auth_request` 共用同一个决策函数**（[原型发布与访问机制.md](./原型发布与访问机制.md) §5.1）。因此本期可以在**没有 nginx** 的情况下端到端跑通"发布 → 三档访问 → 访问记录"全链路。

需要额外注意的一点：给 nginx 用的 `/api/access/check` 虽然是生产放行路径，但它是一个普通 HTTP 接口，**本地可以用 curl 伪造 nginx 会发的请求头来验证**（状态码 + `X-Proto-Release-Dir` 响应头）。因此不存在"要等部署才能验"的盲区——这件事必须在 M4 就验掉，否则生产第一次上线时才发现契约不对。

## 3. 实现前必须先定死的约定

> 这一节的目的是**消灭返工**：下面这些如果边做边改，会同时改两头（前后端）、改契约、改测试。

### 3.1 仓库结构与命名

```
protoHub/
├── docs/                              ← 设计文档（已存在，实现期持续回写）
├── apps/
│   ├── admin/                         ← vben-admin 5.7.0 的 web-antd 变体裁剪而成
│   └── server/                        ← NestJS 11 + Fastify
├── packages/
│   ├── shared/                        ← 契约类型 + 常量 + 错误码（前后端共用）
│   └── db/                            ← Prisma schema / 迁移 / seed
├── scripts/                           ← 冒烟脚本、一致性检查脚本
├── pnpm-workspace.yaml
├── turbo.json
└── package.json
```

| 约定 | 值 |
| --- | --- |
| 包名 | `@protohub/admin`、`@protohub/server`、`@protohub/shared`、`@protohub/db` |
| 服务端端口 | `3100`，**只监听 `127.0.0.1`** |
| 管理台端口 | `5671`，访问一律用 `http://127.0.0.1:5671`（原设计 `5666`/vben 默认；本机 5666–5670 被其他项目占用，见 §9 DEV-1；vite 已开 `strictPort`） |
| 数据库 | `protohub`（开发）、`protohub_test`（集成/冒烟，由同一套迁移创建） |
| 连接串 | `postgresql://postgres:postgres@127.0.0.1:5432/protohub` |
| 存储根 | 开发 `~/protohub-storage`（`tmp/`、`releases/`、`manifests/`、`trash/`） |
| 接口前缀 | `/api`；响应包 `{code,data,error,message}`，成功 `code=0` |

> 用 `127.0.0.1` 而不是 `localhost`：`localhost` 会同时解析到 `::1` 与 `127.0.0.1`，若同端口上有别的进程占了其中一族地址，请求会打到别人的服务上，排查极其费时。

### 3.3 本地运行与环境变量（开发）

```bash
# 首次
pnpm install
pnpm db:migrate            # 建表（含 protohub_test）
pnpm db:seed               # 权限/角色/菜单/超管，幂等
pnpm dev:server            # 127.0.0.1:3100
pnpm dev:admin             # 127.0.0.1:5671，/api 代理到 3100
```

服务端本地 `.env.development`：

| 变量 | 开发值 | 说明 |
| --- | --- | --- |
| `HOST` / `PORT` | `127.0.0.1` / `3100` | |
| `DATABASE_URL` | 指向 `protohub` | |
| `PUBLIC_BASE_URL` | `http://127.0.0.1:3100` | **开发期原型链接指向 Node**（管理台在 5671，端口不同） |
| `STORAGE_ROOT` | `~/protohub-storage` | |
| `SERVE_STATIC` | `node` | 无 nginx 时由 Node 直出 |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` / `SESSION_COOKIE_SECRET` / `ACCESS_TOKEN_SECRET` | 开发用固定假值，但**四个必须互不相同** | 与生产同名变量，代码里不许有默认值 |
| 其余阈值 | 见 [部署与运维方案.md](./部署与运维方案.md) §2 | 直接用文档给的默认值 |

**开发期两个必须记住的行为差异**（不做会白白卡半天）：

1. **Cookie 不能带 `Secure`**：代码里按 `NODE_ENV === 'production'` 判断，开发下不加 `Secure`，否则浏览器在 http 下根本不保存 Cookie，member 档与 refresh 都会失效。
2. **管理台 5671 与原型 3100 是同域不同端口，Cookie 是共享的**（Cookie 不区分端口）。所以 member 档在开发环境可以正常测；但 `accessToken` 存在 localStorage，**跨端口不共享**，这是正常的（原型访问本来也不靠 `Authorization`）。

### 3.4 统一响应、错误码、分页

严格按 [后端接口设计.md](./后端接口设计.md) §1.2 / §1.4 / §1.3 实现，两条最容易被写错的：

1. **`error` 字段放人话**，`errorCode` 放机器码。vben 的错误提示取的是 `responseData.error ?? responseData.message`，把错误码塞进 `error` 会让界面弹出一串大写常量。
2. **401 只用于"未登录/令牌失效"，403 只用于"权限不足"**。vben 只在 401 时刷新令牌，写反会导致用户被莫名登出或该刷新时不刷新。

### 3.5 共享契约包 `packages/shared`

**先冻结它，再实现两端**。内容：

```
packages/shared/src/
├── api-types/          auth.ts user.ts menu.ts project.ts prototype.ts release.ts
│                       accesslog.ts dashboard.ts system.ts common.ts（PageResult 等）
├── constants/
│   ├── permissions.ts        PERMISSIONS 常量（唯一来源，seed 与一致性检查都读它）
│   ├── error-codes.ts        稳定错误码
│   ├── reserved-codes.ts     保留字
│   └── code-rule.ts          CODE_RULE + genProjectCode + genPrototypeCode
└── enums.ts            原型/项目状态、访问档、任务状态（TS 联合类型 + 取值数组）
```

**为什么必须冻结**：`api-types` 是前后端的接缝，改一个字段名要同时改 DTO、service、前端 api 层、组件与测试。冻结后两端可以各自推进；后续改动集中在 `packages/shared` 一处。

> 约束：`packages/shared` **不含任何运行时依赖**（除 zod），不 import Nest、不 import Vue——两端都要能引它。

### 3.6 测试策略（写清"必须有"的是什么）

| 层级 | 范围 | 是否必须有 |
| --- | --- | --- |
| 单元测试 | 纯函数：`decideAccess`、编码生成与校验、zip 安全校验、路径改写、清单/指纹、数据范围解析、密码强度 | **必须**，逐条列在 §5 各阶段任务里 |
| 契约一致性测试 | 权限码 ↔ DB ↔ 后端 Guard ↔ 前端落点；菜单 `component` ↔ `views` 实际文件；编码规则前后端一致 | **必须**，`pnpm check:consistency` |
| 集成测试 | 上传受理 → Worker → 版本提交（真 DB + 真磁盘）、并发取号、失败清理、seed 幂等 | **必须**，用 `protohub_test` |
| 端到端冒烟 | curl 全链路脚本（登录→建项目→建原型→发布→三档访问→回滚→归档→查记录） | **必须**，`pnpm smoke` |
| 界面实测 | 浏览器人工/browser-use 点测（加载/空/失败三态、权限差异、上传两段进度） | **必须**，Gate 里逐项列 |
| 反证测试 | 故意破坏实验（见 §6.4） | **必须**，一阶段至少覆盖本阶段引入的门禁 |

**集成与冒烟数据库隔离**：`protohub_test` 每次跑前 `migrate reset` + `seed`，不碰 `protohub`。冒烟脚本开头自检 `DATABASE_URL` 是否指向 `_test`，不是就拒绝运行——避免把开发数据清掉。

### 3.7 工程约定（红线清单）

**必须遵守**

| 约定 | 说明 |
| --- | --- |
| 不改 `packages/**` | 那是 vben 框架代码。业务只写在 `apps/` 内；框架配置通过 `apps/admin/src/preferences.ts` 覆盖 |
| 通用能力收敛一处 | 两处以上用到的能力抽成一个基础组件/工具，业务差异用 props/参数表达；基础实现遵守开闭原则（新增场景不改基础源码） |
| 复用既有能力 | 表格/分页/表单/抽屉/弹窗用 vben 的 `useVbenVxeTable`/`useVbenForm` 与 ant-design-vue 原生组件，**不自绘同类能力**；服务端不手写 HTTP/JSON/解压的等价实现，用 §3.2 白名单里的库 |
| 信息层级显式分级 | 写样式前先按 [前端设计.md](./前端设计.md) §10.1 定"字号/字重/颜色"层级表，同屏只留一个最重元素 |
| 同类信息收敛一处 | 同一信息不在两处展示；详情页字段只放新建字段 + 系统生成信息 |
| 交互走组件库标准语义 | 偏离 ant-design-vue 标准行为前先问，不默默自创 |
| 注释克制 | 只在 WHY 不明显处写一行（隐藏约束、反直觉的取舍）；不复述代码在做什么 |
| 异常态必须做 | 每个列表/详情都要有加载态、空态、失败态，见 [前端设计.md](./前端设计.md) §10.2 |
| 一次修全同类问题 | 发现某个根因（例如某处漏了 `deleted_at` 过滤）要一次扫遍所有落点，不留"下一阶段再补" |
| 门禁类验证要在干净基线上跑 | 反证实验前先确认基线全绿，否则分不清是"门禁生效"还是"本来就是坏的" |

**禁止**

- 写部署/运维配置（nginx、pm2、CI、备份、监控）。
- 引入 §3.2 白名单之外的依赖。
- 用 `any` / `@ts-ignore` 压过类型错误；用 `.skip` 让测试变绿。
- 在实现里硬编码域名、端口、路径（一律走配置）。
- 把"未验证"当成"已完成"写进 §9。

**nginx 契约（本地无 nginx 也能验，必须验）**

用 curl 伪造 nginx 会发的请求：

```bash
# 放行
curl -i -H 'X-Original-URI: /p/crm/crm-p01/' -H 'X-Real-IP: 127.0.0.1' \
     http://127.0.0.1:3100/api/access/check
# 期望：200 + X-Proto-Release-Dir: releases/9/31/77
# 密码档未解锁 → 401 + X-Proto-Reason: NEED_PASSWORD
# 成员档未登录 → 403 + X-Proto-Reason: NEED_LOGIN
# 编码不存在 → 404 + X-Proto-Reason: NOT_FOUND
# 伪造公网来源（X-Real-IP: 8.8.8.8）→ 403
```

| # | 检查 | 预期 |
| --- | --- | --- |
| C1 | 200 时必须带 `X-Proto-Release-Dir`，形状为 `releases/{数字}/{数字}/{数字}` | 漏了这头生产会 404；形状不对会被 nginx 白名单 map 拦掉 |
| C2 | 401/403/404 时带 `X-Proto-Reason` | 门面页靠它选形态 |
| C3 | 非内网 `X-Real-IP` → 403 | 防被当权限探测 API 用 |
| C4 | 接口**不接受任何凭据参数**（query/body 里的 token 一律不认），只认 Cookie | 同上 |

**Cookie 契约**

| Cookie | Path | 属性 | 实测点 |
| --- | --- | --- | --- |
| `proto_access_p{原型ID}` | `/p/{项目编码}/{原型编码}` | HttpOnly、SameSite=Lax、开发无 Secure、Max-Age 86400 | 浏览器 Application 面板核对；换一个原型访问时**不带**这个 Cookie |
| `proto_sess` | `/` | 同上 | 登录后出现；登出后消失 |
| `proto_refresh` | `/api/auth` | 同上 | 仅在 `/api/auth/**` 请求中出现 |

## 8. 实施期常见失败模式与对策

按"最容易踩到"排序。这些坑的共同点是：**错误不会立刻报错，而是在别的地方以看不懂的形式出现**。

| # | 失败模式 | 症状 | 对策 / 在哪一步发现 |
| --- | --- | --- | --- |
| F-1 | `refresh` 返回了包装结构 | 登录正常，之后所有请求头变成 `Bearer [object Object]`，页面全空 | M1 认证契约第 2 条；N3 |
| F-2 | 401/403 写反 | 该刷新时不刷新（用户被登出）或越权时疯狂刷新 | M1 认证契约第 3/4 条；N4 |
| F-3 | 菜单 `component` 路径写错 | 点菜单进 404，控制台一行 `route component is invalid` | M1 Gate + 一致性脚本；N2 |
| F-4 | 忘了给某写接口标 `@RequirePermission` | 前端隐藏了按钮，但直接调接口能成功 | M5-T4 审计 + 权限矩阵实测；N5 |
| F-5 | 单条查询漏 `applyDataScope` | 列表看不到别人的项目，但猜到 id 就能打开详情 | M2-T2 单测（单条路径必须单独测）；N6 |
| F-6 | 忘了 `deleted_at is null` 过滤 | 删掉的项目/原型又出现 | M2 单测覆盖软删除；一致性检查 |
| F-7 | 解锁 Cookie 签名没绑 `policy_version` | 改密码后老浏览器仍能看，安全承诺失效 | M4-T8；N7 |
| F-8 | HTML 被缓存 | 切版本/改密码后用户说"我这边还是旧的" | M4-T5/G7 `curl -I` 钉死；N8 |
| F-9 | 上传同步解压 | 100MB 包导致请求超时，任务卡死无记录 | M3-T2 必须只做轻校验并异步；M3-T4 worker |
| F-10 | 用 `max(id)+1` 猜 `releaseId` 拼目录 | 并发下两个任务写同一目录，产物互相覆盖 | M3-T8 明确禁止；M3-T16 并发集成测试 |
| F-11 | 先写库后 `rename` | 库里有记录、磁盘没目录 → 永久 404 且不自愈 | M3-T8 顺序约束；失败清理集成测试 |
| F-12 | 保留版本按项目算 | 一个原型发 6 个版本后只剩 1 个能回滚 | M5 GC 判据第 2 条（20 原型各 2 版本，一个都不删） |
| F-13 | 开发环境 Cookie 带了 `Secure` | 登录后立刻被踢、member 档永远 403 | §3.3 第 1 条；M1-T6 实测 Cookie 属性 |
| F-14 | 用 `localhost` 访问自建服务 | 偶发连到别的进程、接口行为诡异 | §3.1 约定；一律 `127.0.0.1` |
| F-15 | 数据权限/权限码缓存设成永久 | 改权限后不生效，只能重启 | M1-T7 30s TTL + 主动失效；M1 Gate G4 |
| F-16 | 种子不幂等 | 第二次 seed 报错，或覆盖了运维手工调的权限 | M1-T3 连跑两次 |
| F-17 | 访问日志同步写库 | 静态访问变慢，库写入失败还会 500 | M4-T9 异步批量 + 写失败只落日志 |
| F-18 | 前端自绘组件 | 与 vben 主题/交互不一致，后续到处对不齐 | §3.7 红线；M2 Gate 组件复用检查 |
| F-19 | 顺手改了 `packages/**` | 后续无法同步 vben 上游 | §3.7 红线；code review 时 grep |
| F-20 | 用"看起来对"代替实测 | 交付时才发现契约/属性/权限都不对 | 每阶段 Gate 都要求命令跑过 + 界面点过，§9 记证据 |
