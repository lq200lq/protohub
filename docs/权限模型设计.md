# 权限模型设计

> 状态：设计待评审 ｜ 日期：2026-10-06 ｜ 关联：平台设计方案.md §8.5、数据库设计.md §4.3、后端接口设计.md §2

本文是**权限码取值、角色定义、数据权限口径、认证语义**的唯一权威来源。表结构见 [数据库设计.md](./数据库设计.md) §4.3，接口结构见 [后端接口设计.md](./后端接口设计.md) §2。

---

## 1. 设计目标与边界

**目标**

1. 用户、角色、权限码三级可配置，改权限不需要发版。
2. 控制粒度到"接口"，而不只是"菜单能不能看见"——前端绕过界面直接调接口同样被拦。
3. 项目可见范围可控（能做什么 ≠ 能看哪些项目，两个维度分开管）。
4. 变更即时生效：改角色权限、禁用用户、改访问密码后立即起作用。

**边界（不做）**

- 不做 ABAC / 行级策略表达式（如"金额 > 1000 的单据"这类规则引擎）。
- 不做多租户隔离（一期单组织）。
- 不做"临时授权/审批流"。

## 2. 模型总览

```
 sys_user ──< sys_user_role >── sys_role ──< sys_role_permission >── sys_permission
     │                              │                                    │
     │                              │                              (权限码字典)
     │                              └──< sys_role_menu >── sys_menu
     │                                       (菜单/按钮树, 驱动前端路由)
     │
     └──< proto_project_member >── proto_project
              (数据权限: 我能看哪些项目)

维度一：功能权限 → 权限码（能做什么）
维度二：数据权限 → data_scope + 项目成员（能看哪些）
维度三：菜单可见性 → sys_role_menu（界面上显示什么）
```

三者关系：**菜单只管"看不看得见"，权限码管"能不能做"，数据范围管"做在哪条数据上"**。一个用户可能有 `proto:project:list` 但 `data_scope=own`，结果就是"能看到列表菜单，但列表里只有自己的项目"。

## 3. 权限码清单（唯一权威）

命名规范：`{域}:{资源}:{操作}`，全小写，冒号分隔。操作取值统一为 `list` / `read` / `create` / `update` / `delete` / 动词（如 `publish`、`rollback`、`resetpwd`）。新增权限码时**必须同时**在 `sys_permission` 初始化数据与本文档中登记。

### 3.1 工作台

| 权限码 | 说明 |
| --- | --- |
| `dashboard:workspace:view` | 查看工作台首页 |

### 3.2 项目（容器）

管的是"这个项目存不存在、谁能看到"。

| 权限码 | 说明 | 备注 |
| --- | --- | --- |
| `proto:project:list` | 查看项目列表 | 结果受 `data_scope` 过滤 |
| `proto:project:read` | 查看项目详情（含其下原型列表） | |
| `proto:project:create` | 新建项目 | 编码可留空自动生成 |
| `proto:project:update` | 编辑项目（名称/说明/成员） | 项目编码不可改，见 D-14 |
| `proto:project:delete` | 删除项目（级联其下全部原型与产物） | 高危，记审计日志 |
| `proto:project:archive` | 归档/下架项目（其下所有原型链接不再可访问，产物保留） | |

### 3.3 原型（分享与鉴权的最小单位）

| 权限码 | 说明 | 备注 |
| --- | --- | --- |
| `proto:prototype:list` | 查看原型列表 | 随项目可见性，不单独过滤 |
| `proto:prototype:read` | 查看原型详情（含版本记录、发布报告） | |
| `proto:prototype:create` | 新建原型（含首次上传发布时一并创建） | 编码可留空自动生成 |
| `proto:prototype:update` | 编辑原型（名称/说明） | 原型编码不可改，见 D-14 |
| `proto:prototype:delete` | 删除原型（含其全部版本产物） | 高危，记审计日志 |
| `proto:prototype:archive` | 归档/下架原型（该链接不再可访问，产物保留） | 只影响这一个原型的链接 |
| `proto:prototype:policy` | 修改访问策略（公开/密码/仅成员、改密码） | 单独授权，区别于普通编辑 |
| `proto:prototype:publish` | 上传并发布新版本 | |
| `proto:prototype:rollback` | 回滚到历史版本 | |

### 3.7 权限码与"菜单按钮"的关系

- `/auth/codes` 返回的是**用户通过角色获得的权限码全集**（来自 `sys_role_permission`），用于前端 `hasAccessByCodes` / `v-access:code` 判断。
- `sys_menu` 中 `type='button'` 的节点携带 `auth_code`，作用是**按菜单维度给角色配权**（角色分配界面以菜单树+按钮为骨架），本身不额外产生权限；最终权限仍以 `sys_role_permission` 为准。
- 因此：新增一个按钮权限 = 加一条 `sys_permission` + 在 `sys_menu` 对应菜单下加 `type='button'` 节点（便于配权时勾选）+ 代码里用 `@RequirePermission('xxx')` 与 `v-access:code="['xxx']"`。

## 4. 内置角色

| 角色标识 | 名称 | 数据范围 | 权限范围 | 可删除 |
| --- | --- | --- | --- | --- |
| `super_admin` | 超级管理员 | `all` | 全部权限码 | 否 |
| `admin` | 平台管理员 | `all` | 除 `system:menu:*`、`system:role:assignperm` 外的全部 | 否 |
| `publisher` | 发布者 | `member` | `dashboard:*`；`proto:project:list/read/create/update`；`proto:prototype:list/read/create/update/policy/publish/rollback`；`proto:release:list`；`proto:accesslog:list` | 否 |
| `viewer` | 只读访客 | `member` | `dashboard:*`；`proto:project:list/read`；`proto:prototype:list/read`；`proto:release:list`；`proto:accesslog:list` | 是 |

> **注意 publisher 不包含任何 `delete`**：删除项目/原型会连同全部版本产物一起消失且不可恢复，因此默认不给日常使用者，需要时单独授权（或临时提权给 `admin`）。这是刻意的：把最危险的动作挡在默认权限之外。

**约束（必须在后端强制，不只是前端隐藏）**

| 编号 | 约束 | 原因 |
| --- | --- | --- |
| C-1 | 内置 4 个角色的 `code` 不可修改、不可删除 | 代码与初始化数据依赖这些标识 |
| C-2 | 任何操作都不能删除/禁用最后一个 `super_admin` 用户 | 否则平台永久失去管理入口 |
| C-3 | 用户不能删除自己、不能撤销自己的 `super_admin` 角色 | 防误操作锁死 |
| C-4 | 非 `super_admin` 不能给他人分配 `super_admin` 角色 | 防提权 |
| C-5 | `super_admin` 在 Guard 中短路放行（不查权限码表） | 避免超级管理员被自己改坏权限后失去入口 |
| C-6 | 数据范围取该用户所有角色中**最宽**的一个 | 多角色场景的直觉预期（有 all 就是 all） |

## 5. 认证设计

### 5.1 令牌与 Cookie

| 凭据 | 形式 | 有效期 | 存放 | 用途 |
| --- | --- | --- | --- | --- |
| accessToken | JWT（HS256） | 2 小时 | 前端内存 + vben `accessStore` 持久化 | 管理台接口 `Authorization: Bearer <token>` |
| refreshToken | JWT（HS256，独立密钥） | 7 天，每次刷新轮转 | **HttpOnly Cookie** `proto_refresh`，`Path=/api/auth`，`SameSite=Lax`，生产加 `Secure` | 仅用于 `/auth/refresh` |
| 会话 Cookie | 签名载荷 `v1.{userId}.{tokenVersion}.{exp}.{sig}` | 7 天 | **HttpOnly Cookie** `proto_sess`，`Path=/`，`SameSite=Lax`，生产加 `Secure` | **仅供原型访问决策**（member 档判定身份） |

accessToken 载荷：`{ sub: userId, username, tv: tokenVersion, jti, iat, exp }`。

**为什么需要第三个凭据（`proto_sess`）**：浏览器发起的**顶层导航与静态资源请求不会携带 `Authorization` 头**（该头只由 JS 主动设置），所以"仅内部成员可见"的原型在被直接打开时，服务端根本收不到 Bearer token。用一个作用域为 `/` 的 HttpOnly 会话 Cookie 承接这个场景，是唯一可行且不把 token 暴露给 JS 的方案。细节与 SameSite 限制见 [原型发布与访问机制.md](./原型发布与访问机制.md) §5.4。

### 5.2 状态码语义（前端行为完全依赖这三条，不能随意改）

| 状态码 | 含义 | 前端行为（vben 既有实现） |
| --- | --- | --- |
| **401** | 未登录 / accessToken 无效或过期 | 触发自动刷新：调 `/auth/refresh`，成功后重放原请求；失败则跳登录页或弹"登录过期" |
| **403** | 已登录但权限不足 | 直接提示错误文案，**不刷新令牌** |
| 400 | 参数错误 | 提示 `message` |
| 500 | 服务端异常 | 提示通用错误 |

> 实测依据：`packages/effects/request/src/request-client/preset-interceptors.ts` 中 `authenticateResponseInterceptor` 仅在 `response.status === 401` 时进入刷新逻辑；其余错误交给 `errorMessageResponseInterceptor`。业务接口把"token 过期"错写成 403 会导致用户被强制登出——这是必须避免的实现错误。

### 5.3 refresh 接口的特殊返回（实测，容易写错）

```
POST /api/auth/refresh
请求：无 body，浏览器自动携带 proto_refresh Cookie（前端 withCredentials: true）
成功：HTTP 200，响应体是【裸字符串】（新的 accessToken），不是 {code,data,...} 包装
失败：HTTP 403，响应体为错误包装 {code:-1, data:null, error, message}
副作用：轮转 refresh Cookie（重新 Set-Cookie）
```

原因：vben 的 `refreshTokenApi` 使用的是不挂默认响应拦截器的 `baseRequestClient`（`responseReturn: 'raw'`），代码取值为 `resp.data`（即 axios 的 body）。若后端返回包装结构，`accessStore.accessToken` 会被写成一个对象，后续所有请求的 Authorization 头都会变成 `[object Object]`。

### 5.4 会话撤销（改密码 / 禁用 / 强制下线）

`sys_user.token_version`（int，默认 0）参与 accessToken 载荷。Guard 每次校验时会比对载荷里的 `tv` 与库里的当前值：

| 场景 | 动作 | 效果 |
| --- | --- | --- |
| 修改自己的密码 | `token_version + 1` | 其它设备上的 token 与 `proto_sess` 立刻失效（本机重新登录） |
| 管理员重置他人密码 | `token_version + 1` | 该用户全部在线会话失效 |
| 禁用用户 | `status=0` | Guard 查库发现非启用 → 401 |

因为 accessToken 有效期只有 2 小时且 Guard 查库，撤销的生效上限是"下一次请求"，无需引入额外的黑名单存储。

## 6. 数据权限

### 6.1 `data_scope` 取值

| 值 | 含义 | 列表查询的处理 | 单条访问的处理 |
| --- | --- | --- | --- |
| `all` | 全部项目 | 不加过滤 | 放行 |
| `member` | 我参与的项目（`proto_project_member` 里有我，或我创建的） | 加 `id in (我参与的 ∪ 我创建的)` | 不在集合内 → 403 |
| `own` | 仅我创建的 | 加 `created_by = me` | 非我创建 → 403 |

多角色取最宽（C-6）。

### 6.2 实现要点

- 过滤下沉到**查询构造层**，不要在每个 service 里手写 `if`。做法：项目列表的查询统一走 `ProjectRepo.findPaged(user, filters)`，该方法内部调用 `applyDataScope(query, user)`；详情/写操作统一走 `ProjectRepo.findAccessible(id, user)`，查不到就抛 403（不区分"不存在"与"无权限"，避免探测他人项目是否存在）。
- `proto_project_member` 的角色字段 `member_role`（`owner`/`editor`/`viewer`）**一期只记录与展示，不据此做差异授权**（差异化授权留 P1）；一期实际判断只看"是否在成员表里"。这样避免一期就引入两套并行的权限逻辑。
- **但成员数据本身一期必须有**：`publisher`/`viewer` 的 `data_scope=member` 靠它过滤，成员表为空则这两个角色登录后看不到任何项目（自测时最容易被误判为"数据权限写错了"）。落点：创建项目时把创建人写成 `owner`；管理员通过 `PUT /api/projects/{id}/members` 增删成员。
- **原型不单独判数据权限，一律通过父项目判定**：`PrototypeRepo.findAccessible(id, user)` 内部先取 `project_id`，再复用 `ProjectRepo.findAccessible`。这样"数据范围"只有一处实现；也保证不会出现"能看到项目却看不到它下面某个原型"这种无法向用户解释的状态。同理，`/api/access/check` 里 member 档的可见性判断也调这一个函数。

## 7. 前端接入

### 7.1 与 vben 的契约（必须按此实现，否则登录流程跑不通）

| 接口 | 用途 | 关键点 |
| --- | --- | --- |
| `POST /api/auth/login` | 登录 | 返回 `data.accessToken`（字符串）；同时 Set-Cookie 下发 refreshToken |
| `POST /api/auth/refresh` | 刷新 | 返回**裸字符串**，见 §5.3 |
| `POST /api/auth/logout` | 登出 | 清 Cookie；前端清 store |
| `GET /api/auth/codes` | 权限码 | 返回 `string[]` |
| `GET /api/user/info` | 用户信息 | 必须含 `userId`、`username`、`realName`、`avatar`、`roles: string[]`、`homePath` |
| `GET /api/menu/all` | 动态菜单/路由 | 返回路由树，`component` 字段是相对 `apps/admin/src/views` 的路径字符串 |

### 7.2 三层使用方式

| 场景 | 写法 | 说明 |
| --- | --- | --- |
| 菜单/路由可见性 | 后端 `/menu/all` 只下发有权菜单；需要"可见但拦截"的用 `meta.menuVisibleWithForbidden: true` | 前端不写业务判断 |
| 按钮/区块显隐 | `v-access:code="['proto:prototype:publish']"` 或 `hasAccessByCodes([...])` | 权限码取自 `/auth/codes` |
| 角色判断（仅特殊场景） | `hasAccessByRoles([...])` | 业务界面尽量用权限码，角色判断只用于"是否显示角色管理入口"这类元场景 |

## 8. 后端鉴权实现要点

### 8.1 接口层 Guard

```ts
// 用法：@RequirePermission('proto:prototype:publish')
canActivate(ctx) {
  const payload = this.jwt.verifyAccessToken(ctx);          // 失败 → 401
  const user = await this.userService.getActive(payload.sub); // 不存在/禁用 → 401
  if (user.tokenVersion !== payload.tv) throw new Unauthorized(); // → 401

  if (this.roles.hasSuperAdmin(user)) return true;           // C-5 短路

  const required: string[] = this.reflector.get(PERM_KEY, handler) ?? [];
  if (required.length === 0) return true;                    // 未标注 = 仅需登录

  const codes = await this.permissionService.codesOfUser(user.id);
  if (required.some((c) => codes.has(c))) return true;        // 语义：满足任一即可
  throw new ForbiddenException('缺少权限：' + required.join('/')); // → 403
}
```

**约定**：`@RequirePermission` 的语义是"满足其中任意一个即可"（OR）。需要"同时满足"的场景（目前没有）应另加装饰器，不要用多个装饰器叠加来暗示 AND——装饰器叠加的默认语义是覆盖，容易出坑。

### 8.2 权限码缓存

`codesOfUser` 结果做 **30 秒 TTL 的进程内 LRU 缓存**，key 为用户 ID，以下操作主动失效该 key：改角色权限、改用户角色、禁用用户。

选 30 秒是权衡：完全实时则每个请求多一次联表查询；30 秒内的一致性对内部平台足够，且"撤销类"操作（禁用/改密）走的是 `token_version` 与 `status` 的**不缓存**查询，因此安全相关的变更仍是即时的。

### 8.3 初始化数据

初始化脚本（`deploy/init/01_seed.sql` 或 Prisma seed）必须幂等，内容与顺序：

1. 插入 4 个内置角色（`code` 唯一，冲突则更新名称与数据范围，不动用户已改的权限分配）。
2. 插入全部权限码（`code` 唯一，冲突则更新名称与分组）。
3. 按 §4 的"权限范围"为 `super_admin` 与 `admin` 补齐角色-权限关联（只增不减，避免覆盖运维手工调整）。
4. 插入菜单树（含按钮节点），并为内置角色建立角色-菜单关联。
5. 插入首个超级管理员账号：用户名 `admin`，初始密码随机生成并**打印到部署日志**，且 `force_password_change = true`（首次登录强制改密）。

> 具体字段与 DDL 见 [数据库设计.md](./数据库设计.md) §4.3 与 §6。
